- spec-writer: "스펙 없이 코드를 먼저 쓰는 것은 금지다" → 본문 첫 단락에 "스펙 없이 코드를 먼저 쓰지 않는다" 추가. 나머지 뺀 문장(공통 스펙 우선, interview-me의 질문 방식, adr-writer의 Proposed/Accepted 시점, tdd의 단일 원본·Prove-It, spec-conformance-check의 "맞는 것을 만들었는가")은 본문에 이미 있어 추가하지 않았다.

## 4. CUSTOMIZATIONS 절 초안

**계기**: 스킬 작성 가이드 대조 보고서의 3번 항목(description 축약)의 be-workflow 몫. be-review에서 "핵심 용례 → 사용자 문구 예시 → 반드시 사용하라 → 인접 스킬 경계" 구조가 발동률을 올리고 절차 설명은 발동률에 기여하지 않음이 확인됐으므로 같은 구조로 통일했다.

**규칙**: 발동 뒤 절차·규칙은 본문으로 보내고 description에는 라우팅 정보만 남긴다. 역할 용어 셋만 쓰고 엠대시를 없앤다.

**실측**: 라우팅 케이스 8개(스킬마다 하나)로 전후 비교. 일곱 스킬은 3/3 유지, tdd는 1/3 → 2/3. 합계 1,974자 → 1,677자.

**배운 것**: ① tdd는 "~가 안 된다", "고쳐줘" 같은 문구만으로는 발동하지 않는다. 모델이 한 줄 수정을 "사소한 변경"으로 보고 워크플로우를 건너뛰기 때문이다. "한 줄 수정이라도 코드를 고치기 전에"처럼 사소함을 예외로 인정하지 않는 문장이 있어야 올라간다. ② 평가 프롬프트의 "코드만 고쳐" 같은 말은 측정 대상을 바꾼다. 케이스 프롬프트는 사용자 요청만 담고 도구 제약은 중립적으로 적는다. ③ 측정 중 API 무응답으로 턴 0 시간 초과가 나면 발동 실패와 구분해 재측정해야 한다.

## 5. 새 description 전문

### adr-writer (256자)

되돌리기 비싼 기술 결정을 ADR(Architecture Decision Record)로 남기는 스킬. 사용자가 "ADR 작성", "이 결정 기록해줘", "왜 이렇게 했는지 남겨줘"라고 하거나, 프레임워크·의존성·데이터 모델·DB 스키마·인증 전략·API 아키텍처 결정이 담긴 계획이나 공통 스펙이 승인됐거나, 스펙 적합성 검증을 통과해 Proposed ADR을 확정할 때 반드시 이 스킬을 사용하라. 작업 계획 작성은 task-breakdown을 사용한다.

### interview-me (208자)

모호한 요청에서 사용자의 실제 의도를 끌어내는 인터뷰 스킬. 사용자가 "인터뷰해줘", "질문해줘", "시작 전에 내 생각 점검해줘"라고 하거나, 요청에 대상 사용자·이유·성공 기준·핵심 제약 중 하나라도 빠져 있거나, 계획·스펙·코드를 만들기 전에 빈 요구사항을 추측으로 메꾸고 있다면 반드시 이 스킬을 사용하라. 요구사항이 이미 명확하면 spec-writer를 사용한다.

### plan-executor (192자)

승인된 PLAN.md를 읽어 실행자에게 작업을 위임하고 결과를 검증하는 오케스트레이션 스킬. 사용자가 "계획 실행해줘", "PLAN.md 진행해", "승인했으니 시작해", "작업 실행"이라고 하거나, docs/plan/의 계획 문서를 실행에 옮기려 하면 반드시 이 스킬을 사용하라. 계획을 새로 쓰는 것은 task-breakdown을 사용한다.

### spec-conformance-check (213자)

구현 결과가 승인된 스펙(docs/spec/)의 성공 기준을 실제로 충족하는지 독립 검증하는 스킬. 사용자가 "스펙대로 됐는지 확인해줘", "기능 검증", "적합성 검증"이라고 하거나, plan-executor의 실행이 끝났으면 반드시 이 스킬을 사용하라. 맞는 것을 만들었는지만 보며, 코드 품질·보안·성능은 code-review-and-quality 같은 리뷰 스킬을 사용한다.

### spec-writer (211자)

요구사항을 코드베이스에 근거한 스펙 문서로 쓰는 스킬. 사용자가 "스펙 작성", "요구사항 문서화", "기획서 정리해줘"라고 하거나, 새 기능·프로젝트·여러 파일에 걸친 변경을 시작하는데 docs/spec/에 스펙이 없으면 반드시 이 스킬을 사용하라. 요구사항이 모호하면 먼저 interview-me를, 승인된 스펙을 작업으로 나누는 것은 task-breakdown을 사용한다.

### task-breakdown (210자)

승인된 스펙(docs/spec/)을 실행자가 그대로 수행할 수 있는 PLAN.md로 나누는 스킬. 사용자가 "작업 계획 세워줘", "plan 작성", "구현 계획", "이 기능 어떻게 나눠서 작업하지"라고 하거나, 승인된 스펙을 실행 단위로 나눠야 하면 반드시 이 스킬을 사용하라. 스펙이 없으면 먼저 spec-writer를, 계획 실행은 plan-executor를 사용한다.

### tdd (194자)

테스트를 먼저 쓰고 구현하는 코딩 규율 스킬. 사용자가 "~가 안 된다", "고쳐줘", "버그", "이 기능 구현해줘", "동작 바꿔줘", "테스트 케이스 뽑아줘"라고 하면, 한 줄 수정이라도 코드를 고치기 전에 반드시 이 스킬을 사용하라. 버그는 재현 테스트가 먼저다. 설정 값·문서·정적 텍스트처럼 동작이 바뀌지 않는 변경에는 사용하지 않는다.

### using-agent-skills (193자)

이 워크플로우의 어느 스킬부터 시작할지 정하고 모든 스킬에 공통인 운영 규칙을 담은 메타 스킬. 사용자가 "어디서부터 시작해?", "어떤 스킬 써야 해?", "작업 순서 알려줘"라고 하거나, 새 작업이 도착했는데 진입 스킬이 분명하지 않으면 반드시 이 스킬을 사용하라. 단일 파일·명확한 범위의 사소한 변경은 워크플로우를 건너뛰고 직접 처리한다.
