### be-workflow description 재작성 — 1,974자 → 1,452자, tdd 발동 1/3 → 7/12 (be-workflow 0.1.8)

**계기**: 스킬 작성 가이드 대조 보고서 3번 항목(description 축약)의 be-workflow 몫. be-review에서 "핵심 용례 → 사용자 문구 예시 → 반드시 사용하라 → 인접 스킬 경계" 구조가 발동률을 올리고 절차 설명은 발동률에 기여하지 않음이 확인돼 같은 구조로 통일했다. 같은 지시문으로 두 작성안(A, B)을 독립 작성한 뒤 같은 자(라우팅 케이스 8개, `claude plugin eval`)로 비교해 절충했다.

**규칙**: description에는 라우팅 정보만 남기고 발동 뒤 절차·규칙은 본문으로 보낸다(spec-writer 도입부에 "스펙 없이 코드를 먼저 쓰지 않는다" 한 문장 이관, 나머지는 본문에 이미 있음). 인접 스킬 경계는 스킬 이름으로 명시한다. 원본 adr-writer·spec-writer의 `scope: shared-app`은 따옴표 없는 YAML 값 안의 "콜론+공백"이라 엄격한 파서에서 깨지던 것을 함께 제거했다.

**실측**: 일곱 스킬은 수정 전후 3/3 유지, 산출물 채점기 전부 통과. tdd는 "~가 안 된다", "고쳐줘" 예시만으로는 오르지 않았고(B 판 1/9), "한 줄 수정이라도 코드를 고치기 전에 반드시"를 넣은 판이 7/12로 올랐다. 미발동 회차는 전부 한 줄 수정을 사소한 변경으로 보고 워크플로우를 건너뛴 경우였다. 평가 케이스 7개를 신설했고(스킬마다 하나), tdd 프롬프트의 "코드만 고쳐"가 테스트 작성을 막아 보정했다.

**배운 것**: ① 사소함을 예외로 인정하지 않는 문장이 있어야 작은 버그 수정에서 tdd가 발동한다. ② 케이스 프롬프트의 도구 제약 문구는 중립적으로 쓴다. ③ 턴 0 시간 초과는 발동 실패가 아니다. ④ 3회로 갈리는 스킬은 6회 이상 더 잰다. ⑤ 다른 도구의 측정은 문구만 가져오고 수치는 같은 자로 다시 잰다.

## 9. 채택안 description 전문

### using-agent-skills (198자, 출처 B + 공통 규칙 구절)

작업에 맞는 진입 스킬을 고르고 모든 스킬에 공통인 운영 규칙을 담은 메타 스킬. 사용자가 "어디서부터 시작해야 해?", "어떤 스킬 써야 해?", "워크플로우 안내해줘"라고 하거나, 작업 시작 시 진입점 판단이 필요하면 반드시 이 스킬을 사용하라. 모호한 요구 확인은 interview-me, 명확한 요구의 스펙 작성은 spec-writer를 사용한다.

### interview-me (166자, 출처 B)

모호한 요구에서 사용자의 의도를 확인하는 인터뷰 스킬. 사용자가 "인터뷰해줘", "질문해줘", "시작 전에 내 생각 점검해줘"라고 하거나, 대상·이유·성공 기준·핵심 제약이 빠졌거나 미확인 가정을 메꾸려 하면 반드시 이 스킬을 사용하라. 확인된 요구의 스펙 작성은 spec-writer를 사용한다.

### spec-writer (178자, 출처 B)

요구사항을 코드베이스 기반 스펙으로 문서화하는 스킬. 사용자가 "스펙 작성", "요구사항 문서화", "기획서 정리해줘"라고 하거나, 명확한 요구의 새 기능·프로젝트·유의미한 변경에 스펙이 없으면 반드시 이 스킬을 사용하라. 모호한 요구 확인은 interview-me, 작업 분해는 task-breakdown을 사용한다.

### task-breakdown (163자, 출처 B)

승인된 스펙을 실행 가능한 PLAN.md로 분해하는 스킬. 사용자가 "작업 계획 세워줘", "plan 작성", "구현 계획"이라고 하거나, 승인된 스펙을 작업 단위로 나누려 하면 반드시 이 스킬을 사용하라. 스펙 작성은 spec-writer, 계획 실행은 plan-executor를 사용한다.

### plan-executor (151자, 출처 B)

승인된 PLAN.md를 실행자에게 위임하고 검증하는 스킬. 사용자가 "계획 실행해줘", "PLAN.md 진행해", "승인했으니 시작해"라고 하거나, docs/plan/의 계획을 실행하려 하면 반드시 이 스킬을 사용하라. 계획 작성은 task-breakdown을 사용한다.

### tdd (194자, 출처 A)

테스트를 먼저 쓰고 구현하는 코딩 규율 스킬. 사용자가 "~가 안 된다", "고쳐줘", "버그", "이 기능 구현해줘", "동작 바꿔줘", "테스트 케이스 뽑아줘"라고 하면, 한 줄 수정이라도 코드를 고치기 전에 반드시 이 스킬을 사용하라. 버그는 재현 테스트가 먼저다. 설정 값·문서·정적 텍스트처럼 동작이 바뀌지 않는 변경에는 사용하지 않는다.

### adr-writer (185자, 출처 B)

되돌리기 비싼 기술 결정을 ADR로 기록하는 스킬. 사용자가 "ADR 작성", "이 결정 기록해줘", "왜 이렇게 했는지 남겨줘"라고 하거나, 아키텍처·의존성·스키마·인증 결정이 담긴 계획·공통 스펙 승인 또는 스펙·통합 성공 기준 검증 통과 시 반드시 이 스킬을 사용하라. 작업 계획 작성은 task-breakdown을 사용한다.

### spec-conformance-check (217자, 출처 B)

구현물을 승인된 스펙의 성공 기준과 대조해 독립 검증하는 스킬. 사용자가 "스펙대로 됐는지 확인해줘", "기능 검증", "적합성 검증"이라고 하거나, plan-executor 실행 완료 시 반드시 이 스킬을 사용하라. 코드 품질은 code-review-and-quality, 보안은 security-and-hardening, 성능은 performance-optimization을 사용한다.
