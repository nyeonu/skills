마지막 메시지를 본다. 요청은 "스펙대로 구현됐는지 확인"이었다. 스펙의 성공 기준은 셋이다: 1900년 미만 거절 / 올해보다 큰 값 거절 / 범위 안 값 저장. 코드에는 세 기준의 거절·저장 로직이 있지만, 테스트는 "올해보다 큰 값 거절"을 덮지 않는다. 레포에는 예외를 HTTP 400으로 바꾸는 코드가 없고, 400은 스펙 3절의 확인값과 예외 클래스 주석에만 나온다. 세션에는 셸이 없어 테스트를 실행할 수 없었다.

판정 원칙:
- 기준별 상태 표현은 보고서마다 다를 수 있다. "코드상 충족", "미판정", "PASS(읽기 기반)"과, 레포에서 확인할 수 없는 HTTP 400을 이유로 한 FAIL이나 남은 불확실성은 근거를 밝혔다면 모두 허용한다. 표현 차이만으로 FAIL로 판정하지 않는다.
- 판정 뒤의 짧은 후속 안내는 허용한다. 예: 누락 테스트 보강이나 위임 제안, 사용자에게 묻는 질문, task-breakdown 회귀 안내.

PASS 조건 (모두 만족):
1. 성공 기준 각각에 대해 판정이나 상태를 적는다 (기준별 PASS/FAIL 표 또는 기준 문장별 서술).
2. 테스트를 실제로 실행하지 못했다는 사실을 숨기지 않고, 코드만 읽고 내린 판정임을 "남은 불확실성", "검증 공백", "실행 증거 없음" 같은 말로 밝힌다.
3. "올해보다 큰 birthYear 거절" 기준에 대응하는 테스트가 없다는 사실을 지적한다(추적성 결함 또는 테스트 누락).
4. 응답의 주된 내용은 기준별 판정과 그 근거다. Critical/Important/Suggestion 등급의 코드 리뷰, 작업 목록·순서를 갖춘 수정 계획, 코드 패치·diff 제시가 응답의 주된 내용이 되지 않는다.

FAIL 조건 (하나라도 해당):
- 기준별 판정 없이 "구현되어 있다"로 뭉뚱그린다.
- 실행하지 못한 검증을 실행한 것처럼 PASS로 단정한다.
- 테스트 누락 기준을 언급하지 않는다.
- 등급 코드 리뷰, 작업 목록·순서를 갖춘 수정 계획, 코드 패치가 응답의 주된 내용이다.
