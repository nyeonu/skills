# TDD (Test-Driven Development)

실패하는 테스트를 먼저 쓰고, 그것을 통과시키는 코드를 쓰는 규율이다. 테스트가 곧 증거다 — "된 것 같다"는 완료가 아니다. 에이전트가 코드를 쓰는 환경에서 테스트는 사람이 에이전트의 완료 주장을 믿을 수 있는 유일한 계약이다.

addyosmani `test-driven-development`를 이 워크플로우에 맞게 포크하고, 테스트 케이스 도출 방법론(5출처)을 신설한 버전이다.

## 워크플로우 상 위치

이 스킬은 코드 작성 규율의 **단일 원본**이다. 두 경로로 작동한다:

- **파이프라인 밖 코딩** (버그 수정, 소규모 변경): 이 스킬이 직접 발동한다.
- **파이프라인 안 코딩** (task-breakdown → plan-executor): 하위 에이전트는 스킬을 로드하지 않으므로, task-breakdown이 이 규율을 PLAN.md의 작업 구조에, plan-executor가 하위 에이전트 지시문에 새겨 넣는다. 규율의 내용이 바뀌면 이 문서만 고친다 — 두 스킬은 절차를 복제하지 않고 참조한다.

## 스택 발견 우선

TDD 사이클은 보편이지만 명령은 레포마다 다르다. 첫 테스트를 쓰기 전에 **이 레포가 어떻게 테스트하는지** 파악하고, 이후 모든 단계에서 그 명령을 쓴다:

- 빌드 시스템과 체크인된 래퍼 (`./gradlew`, `./mvnw`, `make test`, 레포 스크립트) — 전역 도구보다 우선
- 단일 테스트 실행 명령(루프 중)과 전체 스위트 명령(완료 전)의 구분
- 테스트 위치·파일명·이웃 테스트의 패턴 (예: `@DisplayName` 한글 서술, AbstractTest 상속 여부)
- README·CI 워크플로우가 보여주는, 실제로 머지를 막는 명령

`npm test` 같은 기본값을 가정하지 마라 — Gradle·pytest 프로젝트엔 각자의 명령이 있다.

## TDD 사이클

```
RED (실패 테스트 작성) → GREEN (통과할 최소 구현) → REFACTOR (그린 유지하며 정리) → 반복
```

1. **RED**: 테스트를 먼저 쓰고 **실패를 실행으로 확인한다.** 처음부터 통과하는 테스트는 아무것도 증명하지 못한다 — 잘못된 것을 테스트하고 있다는 신호다.
2. **GREEN**: 그 테스트를 통과시키는 최소한만 구현한다. 과설계 금지.
3. **REFACTOR**: 테스트가 그린인 상태에서 중복 제거·이름 개선을 하고, 정리 단계마다 테스트를 재실행한다.

## Prove-It 패턴 (버그 수정)

버그 리포트가 오면 **수정부터 시작하지 마라.** 순서는 고정이다:

1. 버그를 재현하는 테스트를 작성한다
2. 테스트 실패로 버그 존재를 확인한다 (실패하지 않으면 재현을 못 한 것 — 수정에 들어가지 마라)
3. 수정을 구현한다
4. 테스트 통과로 수정을 증명한다
5. 전체 스위트로 회귀 없음을 확인한다

이 테스트는 수정 후에도 남아 같은 버그의 재발을 막는다 (도출 출처 ⑤).

## 테스트 케이스 도출 — 5출처

테스트 단위는 "생각나는 것"이 아니라 **"출처가 있는 것"**이다. 떠오르는 대로 만들면 반드시 모자란다. 각 테스트는 아래 출처 중 하나에서 기계적으로 파생되고, 테스트 옆에 출처를 적을 수 있어야 한다. 출처를 다 돌았는데 안 나오는 케이스는 스펙에도 없는 케이스다 — "모자람"이 "스펙의 구멍"으로 드러난다.

| # | 출처 | 도출 방법 |
|---|---|---|
| ① | 스펙 성공 기준 (SC-N) | SC 하나당 최소 테스트 하나 — 정상 경로. 대응 테스트 없는 SC는 검증 없이 출시되는 것이다. |
| ② | 동등 분할·경계값 | 같은 동작을 하는 입력끼리 묶어 묶음당 대표 1개 (예: 존재하는 ID / 없는 ID / 형식 오류 / 누락). 경계에서 1개씩 (0건·1건·최대·최대+1). |
| ③ | 오류 분기 | 코드(설계)의 모든 `if`·의존성 실패(외부 API 타임아웃, 캐시 미스, 권한 없음)에 이름을 붙인다. **분기를 설명하는 테스트 이름을 못 짓겠으면 그 분기가 불필요하거나 스펙 누락이다.** |
| ④ | 상태·순서 | 같은 요청 2회(멱등성), 수정 직후 조회(캐시 일관성), 동시 요청, 트랜잭션 실패 시 복원. |
| ⑤ | 과거 버그 | Prove-It으로 쌓인 재현 테스트. 시간이 지나며 가장 값진 층이 된다. |

**모자람 사후 점검**: "구현 코드에서 이 한 줄을 지우면 실패하는 테스트가 있는가?" 없으면 그 줄이 테스트가 모자란 곳이다. 라인 커버리지 숫자보다 이 질문이 정확하다.

## 테스트 층 판정

피라미드 비율은 유닛 ~80% / 통합 ~15% / E2E ~5%. 층 판정 기준:

- **순수 로직** (변환, 검증, 조립) → 유닛 (밀리초, I/O 없음)
- **실제 인프라가 있어야만 검증되는 동작** → 통합 (테스트 DB·로컬 Redis). **목(mock) 기반 유닛으로 대체 불가** — 트랜잭션 롤백, 캐시 무효화의 실제 적중, HTTP 상태·오류 code가 FE까지 도달하는 계약이 여기 속한다. "무효화 함수가 호출됐다"(유닛)와 "캐시가 실제로 지워졌다"(통합)는 다른 명제다.
- **크리티컬 사용자 경로** → E2E, 최소한만

목은 최후 수단이다: 실제 구현 > 페이크(인메모리 대체) > 스텁(고정 응답) > 목(호출 검증). 전부 목이면 테스트는 통과하는데 프로덕션이 깨진다.

## 좋은 테스트 원칙

- **상태를 검증하라, 내부 호출을 검증하지 마라.** "정렬된 결과가 반환된다"(상태)를 검증하고, "쿼리에 ORDER BY가 포함됐다"(구현)를 검증하지 마라 — 후자는 리팩토링만 해도 깨진다.
- **테스트 코드는 DRY보다 DAMP.** 각 테스트가 공유 헬퍼를 추적하지 않고도 혼자 읽히게 쓴다. 테스트의 중복은 자기완결성을 위한 비용으로 수용한다.
- **이름은 동작 명세다.** "SC-N: 저장된 birthYear가 조회 응답에 채워진다"처럼 기대 동작을 서술한다. 스펙 기반 작업이면 `@DisplayName("SC-N: …")` 형식으로 SC ID를 태깅한다 — spec-conformance-check가 이 태그로 매핑을 확인한다. **스펙을 통합·재번호하면 테스트 태그도 같이 리매핑한다** — 안 하면 추적성이 장식이 된다.
- **테스트 작성과 구현은 분리될수록 강하다.** 구현을 아는 에이전트가 쓴 테스트는 구현의 거울이 된다 — 구현이 틀려도 통과한다. 파이프라인에서는 테스트 작성과 구현을 별도 작업(별도 에이전트)으로 분리하는 것이 이 원칙의 실현이다.

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "코드부터 쓰고 테스트는 나중에" | 나중은 오지 않는다. 사후 테스트는 동작이 아니라 이미 쓴 구현을 테스트한다. |
| "너무 간단해서 테스트가 필요 없다" | 간단한 코드는 복잡해진다. 테스트는 기대 동작의 문서이기도 하다. |
| "수동으로 확인했다" | 수동 확인은 남지 않는다. 내일의 변경이 오늘의 확인을 조용히 깨뜨린다. |
| "테스트가 안 통과하니 skip / 단언 완화하자" | 테스트 약화는 실패를 감추는 것이다. 통과가 목적이 아니라 동작이 목적이다. 통과 못 하면 그 사실을 보고하라. |
| "목으로 하면 유닛으로 다 되는데" | 호출 검증은 동작 검증이 아니다. 롤백·캐시 무효화는 실제 인프라 없이 증명되지 않는다. |
| "프로토타입이니까" | 프로토타입은 프로덕션이 된다. 첫날의 테스트가 테스트 부채 위기를 막는다. |
| "테스트가 첫 실행에 통과했다, 잘 짰네" | RED 없는 GREEN은 검증이 아니다. 잘못된 것을 테스트하고 있을 확률이 높다. |

## 레드 플래그

- 실패를 확인하지 않고 통과한 신규 테스트
- 재현 테스트 없는 버그 수정
- 출처(①~⑤)를 댈 수 없는 테스트, 대응 테스트 없는 SC
- skip·비활성화된 테스트가 남은 채 "전체 통과" 보고
- 레포의 실제 테스트 명령을 확인하지 않고 기본값(`npm test`) 사용

## 검증

작업 종료 전 확인:

- [ ] 레포의 실제 테스트 명령을 파악하고 사용했는가
- [ ] 모든 신규 테스트의 실패(RED)를 실행으로 확인했는가
- [ ] 버그 수정에 재현 테스트가 포함됐는가
- [ ] 도출한 테스트마다 출처(①~⑤)가 있는가, 대응 테스트 없는 SC가 없는가
- [ ] 실제 인프라가 필요한 동작(롤백·캐시 등)을 목 유닛으로 때우지 않았는가
- [ ] 전체 스위트를 레포 명령으로 실행해 통과했는가 (skip 0)
