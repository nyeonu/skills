# 스킬 사용법 (메타 라우터)

## 개요

이 저장소는 개발 단계별 워크플로우 스킬 모음이다: 정의 → 스펙 → 계획 → 실행 →
검증 → 리뷰 → 기록. 이 메타 스킬은 (1) 지금 작업에 맞는 진입 스킬을 고르고,
(2) 모든 스킬에 공통으로 걸리는 운영 규칙을 강제한다. 각 단계의 상세 규칙은 해당
스킬의 SKILL.md가 원본이다.

## 진입점 라우팅

모든 작업이 1번부터 시작하지 않는다. 작업 성격을 보고 해당 스킬로 진입한다.

```
작업 도착
    │
    ├── 사소한 변경(단일 파일·명확한 범위)? ──→ 워크플로우 생략, 직접 처리
    ├── 요구사항이 모호? ───────────────────→ interview-me
    ├── 요구사항 명확, 스펙 없음? ───────────→ spec-writer          [사람 승인 게이트]
    ├── 승인된 스펙 있음? ──────────────────→ task-breakdown       [사람 승인 게이트]
    ├── 승인된/진행 중 계획 있음? ───────────→ plan-executor
    ├── 버그·장애? ────────────────────────→ 디버깅 후, 수정 범위 크면 task-breakdown으로 합류
    ├── 구현 끝, 스펙 충족 확인 필요? ────────→ spec-conformance-check
    ├── 코드 품질 리뷰? ────────────────────→ code-review-and-quality
    │   ├── 보안 관심사? ──────────────────→ security-and-hardening
    │   └── 성능 관심사? ──────────────────→ performance-optimization
    └── 되돌리기 비싼 결정 기록? ─────────────→ adr-writer
        (계획 승인 직후 Proposed / 스펙 적합성 검증 통과 후 Accepted)
```

진행 상태의 단일 원본은 `docs/spec/`·`docs/plan/` frontmatter의 `status`다. 세션이
끊겨도 문서 status를 읽으면 중단 지점부터 잇는다.

## 공통 운영 규칙

모든 스킬에, 항상 적용된다. 타협 불가.

### 1. 가정을 드러내라
사소하지 않은 구현 전에 세우고 있는 가정을 명시하고 "지금 고쳐주지 않으면 이대로
진행한다"고 알린다. 모호한 요구사항을 조용히 메꾸지 마라. 가장 흔한 실패는 잘못된
가정을 점검 없이 안고 달리는 것이다.

### 2. 혼란은 즉시 관리하라
불일치·모순·불명확한 스펙을 만나면 **멈춘다.** 추측으로 진행하지 않는다. 혼란 지점을
구체적으로 짚고, 트레이드오프를 제시하거나 질문한 뒤 해소되면 계속한다.
- 나쁨: 한 해석을 조용히 골라 맞기를 바란다.
- 좋음: "스펙엔 X인데 기존 코드엔 Y다. 어느 쪽이 우선인가?"

### 3. 필요하면 반론하라
예스맨이 되지 마라. 접근에 명백한 문제가 있으면 직접 지적하고, 구체적 손해를
정량화해 제시하고(예: "지연 ~200ms 추가"), 대안을 낸다. 충분한 정보 위에서 사람이
결정을 뒤집으면 수용한다. 아부는 실패 모드다.

### 4. 단순성을 강제하라
과설계 경향을 능동적으로 억제하라. 마치기 전에 자문: 더 적은 줄로 되는가? 이
추상화가 복잡도값을 하는가? 시니어가 "왜 그냥 …하지 않았나"라고 하지 않겠는가?
지루하고 뻔한 해법을 선호하라. 영리함은 비싸다.

### 5. 스코프를 지켜라
요청받은 것만 건드린다. 이해 못 한 주석 삭제, 무관한 코드 "정리", 인접 시스템
리팩터링, 미사용으로 보이는 코드 임의 삭제, 스펙에 없는 기능 추가 — 전부 금지.
외과적 정밀함이지 요청 없는 개보수가 아니다.

### 6. 가정하지 말고 검증하라
"맞는 것 같다"는 근거가 아니다. 통과한 테스트·빌드 출력·런타임 데이터 같은 증거가
있어야 완료다. 각 스킬의 검증 단계는 국소 점검이고, 모든 변경에 걸리는 기준은:
테스트 통과, 회귀 없음, 런타임에서 동작 확인, 문서 갱신.

## 이 워크플로우의 고유 규칙

원본 스킬 세트엔 없고 우리 워크플로우에만 있는 제약이다.

1. **승인 게이트 2개(스펙·계획)는 생략 불가.** 사람이 통제권을 유지하는 장치다.
2. **추적성 + 독립 검증.** 스펙 성공 기준(SC-N) ↔ 계획 acceptance 매핑을 계획
   단계에서 강제하고(예방), 구현 후 spec-conformance-check로 확인한다. 이 검증자에게는
   **계획 문서를 주지 않는다** — 계획의 잘못된 해석까지 물려받으면 독립 검증이 아니다.
3. **fail-fast.** 앞 게이트가 실패하면 뒤 단계 비용이 발생하지 않는다. FAIL 하나라도
   있으면 품질 리뷰로 넘어가지 않고 계획 수정으로 되돌린다.
4. **병렬 실행은 읽기 전용 작업(리뷰)에만.** 코드 수정은 어떤 경우든 계획 루프
   (task-breakdown → 승인 → plan-executor)를 통한다. 검증자·리뷰어가 "발견한 김에
   고치기"도 금지 — 승인 게이트 우회가 된다.
5. **단일 환경 진행.** 작업 시작 시 Cowork/CLI 중 하나를 정해 끝까지 그 환경에서.
   산출물이 전부 레포 안(`docs/`)이라 다음 작업은 다른 환경에서 시작해도 된다.

## 빠른 참조

| 단계 | 스킬 | 한 줄 요약 |
|------|------|-----------|
| 정의 | interview-me | 계획·스펙·코드 전에 사용자가 진짜 원하는 것을 끌어낸다 |
| 정의 | spec-writer | 코드 기반 스펙과 성공 기준(SC-N)을 문서화한다 |
| 계획 | task-breakdown | 승인된 스펙을 저비용 에이전트가 실행할 PLAN.md로 분해한다 |
| 실행 | plan-executor | 승인된 PLAN.md를 tier 기반으로 위임·실행·검증한다 |
| 검증 | spec-conformance-check | 구현물이 스펙 성공 기준을 실제로 충족하는지 독립 검증한다 |
| 리뷰 | code-review-and-quality | 다축 코드 리뷰(정확성·가독성·유지보수) |
| 리뷰 | security-and-hardening | OWASP 기준 입력 검증·최소 권한·보안 강화 |
| 리뷰 | performance-optimization | 먼저 측정하고, 중요한 병목만 최적화 |
| 기록 | adr-writer | 되돌리기 비싼 결정을 2시점(Proposed→Accepted)으로 기록 |
