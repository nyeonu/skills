# 승인된 스펙의 수정 — 변경 등급 L0·L1·L2 (spec-writer)

승인된 스펙을 고쳐야 할 때 읽는다. 원문은 spec-writer SKILL.md에서 이관했다.

승인 후 스펙을 고쳐야 할 때는 게이트를 다시 타지 않는다. 대신 변경 등급을 판단하고 그에 맞게 처리한다. 원칙은 "합의된 내용이 즉시 문서에 반영되는 것"이다. 에이전트는 사람들의 구두 합의를 모르므로, 갱신되지 않은 스펙은 에이전트에게 틀린 진실이 된다.

| 등급 | 어떤 변경 | 에이전트가 할 일 |
|---|---|---|
| L0 | 스펙 내부. 문구, 확인값 갱신, 미해결 사항 해소, 외부 계약과 무관한 내용 | 고치고 커밋. 알림 불필요 |
| L1 | 계약 변경이지만 additive(기존 소비자를 깨지 않고 더하기만 함. 예: 응답에 선택 필드 추가) | 고치고 커밋한 뒤, 사용자에게 "계약 상대 담당자에게 알림이 필요하다"고 보고한다 |
| L2 | 깨지는 계약 변경. 필드 삭제·의미 변경, 필수 파라미터 추가, 배포 순서 변경 | **고치기 전에** 상대 담당자 확인이 있었는지 사용자에게 묻는다. 확인이 없으면 진행하지 않는다. 확인 방법(구두 합의 후 커밋 메시지 기록, 또는 PR)은 팀이 정한 것을 따른다 |

- 스펙 변경 커밋은 코드 커밋과 섞지 않는다. 메시지 접두어는 `spec:`. 구두 합의를 근거로 한 L2 변경은 메시지에 `<이름>와 구두 합의`를 남긴다.
- 성공 기준을 고칠 때는 문장을 고치고, 그 기준을 가리키는 계획의 추적성 표와 검증 보고의 해당 행도 함께 고친다. 기준에는 식별자가 없고 문장 자체가 키이므로, 문장만 바꾸고 표를 그대로 두면 추적이 끊긴다.
- 스펙 티켓을 다시 열지 않는다. 요구사항 자체가 바뀌어 스펙을 사실상 다시 써야 하면 수정이 아니라 새 변경이므로, 새 스펙을 쓰고 옛 스펙은 `superseded`로 표시한다.
