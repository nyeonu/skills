# Spec Writer

코드 없이 추측으로 구현하는 것을 막는 스킬이다. 스펙은 사람과 에이전트가 공유하는 단일 진실 원본으로, 무엇을 왜 만들고 완료를 어떻게 판별하는지 정의한다. **이 스킬은 스펙 작성(Specify)까지만 수행하고 종료한다** — 계획 수립은 task-breakdown, 구현은 plan-executor의 몫이다. 이 경계를 넘지 마라.

addyosmani `spec-driven-development`의 Phase 1(Specify)을 이 워크플로우에 맞게 포크한 것이다.

## 사용 시점

- 새 기능·프로젝트·여러 파일에 걸친 변경을 시작할 때
- 외부 요구사항(기획서, 메신저, 이메일)을 구현 가능한 문서로 정리할 때
- 아키텍처 결정이 필요한 변경 전
- 여러 애플리케이션이 함께 바뀌는 변경을 시작할 때 (공통 스펙을 먼저 쓴다 — 아래 1단계)

**사용하지 않는 경우**: 한 줄 수정, 오타 교정, 요구사항이 자명하고 자기완결적인 변경. 요구사항이 모호하면(목표·성공 기준·제약·제외 범위 중 하나라도 한 문장으로 쓸 수 없으면) 이 스킬이 아니라 **interview-me부터** 시작한다.

## 작성 절차

### 1. scope 결정

변경이 걸치는 **애플리케이션**(따로 배포되고 담당자가 있는 단위)의 수를 먼저 센다.

- 하나 → `scope: app` 스펙 하나. parent 없음.
- 둘 이상 → **공통 스펙(`scope: shared-app`)을 먼저 쓴다.** 애플리케이션들이 함께 알아야 하는 것만 담는다: 왜 하는가, 애플리케이션 사이의 계약(API·스키마·이벤트), 배포 순서, 통합 성공 기준, `participants`(참여 애플리케이션과 담당자). 애플리케이션 내부에서 할 일은 넣지 않는다. 공통 스펙이 `approved`된 뒤 애플리케이션마다 `scope: app` 스펙을 `parent`를 지정해 따로 쓴다. 한 세션에서 공통 스펙과 자기 애플리케이션 스펙을 이어서 쓰는 것은 허용되지만, 공통 스펙 승인 전에 app 스펙을 승인하지 않는다.

계약은 공통 스펙 한 곳에만 쓴다. app 스펙은 4절에서 공통 스펙을 참조만 하고 내용을 복사하지 않는다. 사용자가 여러 애플리케이션 변경을 app 스펙 하나로 쓰자고 하면, 계약이 어긋날 위험을 한 문장으로 말하고 공통 스펙 분리를 제안한다. 사용자가 그래도 하나로 가겠다고 하면 따른다.

### 2. 가정 표면화

스펙 내용을 쓰기 전에, 지금 하고 있는 가정을 명시하고 확인받는다:

```
내가 하고 있는 가정:
1. <요구사항에 대한 가정>
2. <아키텍처에 대한 가정>
3. <범위에 대한 가정>
→ 지금 정정해달라. 아니면 이대로 진행한다.
```

모호한 요구사항을 조용히 메꾸지 마라. 스펙의 존재 이유가 코드를 쓰기 *전에* 오해를 드러내는 것이다. **미확인 가정이 3개 이상 쌓이면 스펙 작성을 중단하고 interview-me로 전환한다.**

### 3. 코드베이스 확인

대상 코드베이스를 직접 탐색한다(Glob/Grep/Read). 기존 제약·컨벤션·아키텍처와 요구사항이 충돌하는 지점을 찾아 스펙에 반영한다. 충돌을 발견하면 어느 쪽이 우선인지 사용자에게 확인한다 — 충돌을 안고 쓴 스펙은 계획 단계에서 반드시 터진다.

### 4. 스펙 작성

모호한 지시는 검증 가능한 성공 기준으로 재구성한다. 이때 임의의 성능 수치나 목표를 확정하지 마라 — 제안한 수치는 추정값으로 표시하고 사용자 확인을 받는다:

```
요구사항: "대시보드를 빠르게 해달라"

재구성된 성공 기준 (수치는 추정값이다):
§A. 대시보드 로딩 성능
- §A-1: 4G 환경에서 대시보드 진입 → LCP 2.5초 이내
- §A-2: 초기 데이터 요청 → 500ms 이내 응답
→ 이 목표치를 확인해달라. 근거 있는 기준(SLA, 과거 측정치)이 있으면 그 값으로 바꾼다.
```

스펙을 실제로 작성할 때 `references/spec-template.md`를 읽고 frontmatter, 목차 순서와 성공 기준 식별자(`§글자-번호`, 묶음 글자 + 묶음 안 추가 전용 번호) 계약을 그대로 따른다. 전역 순번(SC-1, SC-2…)은 쓰지 않는다. 문장과 분량은 작업 크기에 맞게 조절하고, 필수 항목에 쓸 내용이 없으면 일반론으로 채우지 말고 `없음`이라고 쓴다.

### 5. 저장 및 승인 요청 — 여기서 종료

- 저장 위치와 브랜치는 scope에 따른다. 디렉터리가 없으면 생성한다.
  - `app`: 그 애플리케이션 저장소의 `docs/spec/YYYY-MM-DD-<브랜치명>-<주제>.md`, 현재 브랜치에. 브랜치명은 `git branch --show-current`로 확인하고 `/`는 `-`로 치환한다 (예: `feature/login` → `feature-login`).
  - `shared-app`: 계약을 제공하는 애플리케이션 저장소(또는 팀 공용 문서 저장소)의 `docs/spec/YYYY-MM-DD-<에픽 티켓>-<주제>.md`. **그 변경의 통합 브랜치**에 커밋한다. 통합 브랜치는 에픽 티켓 번호로 딴 브랜치(예: `feature/ASD-2141`)가 있으면 그것이고, 그런 층이 없으면 main이다. 현재 브랜치가 통합 브랜치가 아니면 사용자에게 알리고 어디에 둘지 확인한다. 상대 애플리케이션 담당자는 상대 저장소의 같은 이름 통합 브랜치에서 이 파일을 읽는다.
- `app` 스펙에 `parent`가 있으면, 그 공통 스펙을 실제로 읽어 4절 계약과 배포 순서를 이 스펙의 상위 제약으로 삼는다. 공통 스펙이 `approved`가 아니면 이 스펙은 `draft`로 두고 사용자에게 알린다.
- 사용자에게 스펙 검토를 요청하고 **종료한다.** 승인 후의 작업 분해는 task-breakdown이 별도 세션에서 수행한다.
- 사용자가 승인하면 `status: approved`로 갱신하고 push한다. 이 승인이 첫 번째 게이트다. 승인 조건:
  - `app`(parent 없음): 담당자 승인.
  - `app`(parent 있음): 공통 스펙이 `approved`여야 한다.
  - `shared-app`: `participants` 담당자 전원 승인. 4절(계약·배포 순서)이 확정되지 않았으면 승인할 수 없다.
  - 팀이 Jira를 쓰면 승인 행위는 스펙 티켓을 완료로 옮기는 것이고, frontmatter는 그와 같은 순간에 맞춘다. 사용자가 "티켓 완료했다"고 하면 frontmatter를 `approved`로 바꾸고 push한다.

## 승인된 스펙의 수정

승인 후 스펙을 고쳐야 할 때는 게이트를 다시 타지 않는다. 대신 변경 등급을 판단하고 그에 맞게 처리한다. 원칙은 "합의된 내용이 즉시 문서에 반영되는 것"이다. 에이전트는 사람들의 구두 합의를 모르므로, 갱신되지 않은 스펙은 에이전트에게 틀린 진실이 된다.

| 등급 | 어떤 변경 | 에이전트가 할 일 |
|---|---|---|
| L0 | 자기 스펙 내부. 문구, 확인값 갱신, 미해결 사항 해소, app 스펙의 내부 내용 | 고치고 커밋. 알림 불필요 |
| L1 | 계약 변경이지만 additive(기존 소비자를 깨지 않고 더하기만 함. 예: 응답에 선택 필드 추가) | 고치고 커밋한 뒤, 사용자에게 "`participants` 담당자에게 알림이 필요하다"고 보고한다 |
| L2 | 깨지는 계약 변경. 필드 삭제·의미 변경, 필수 파라미터 추가, 배포 순서 변경 | **고치기 전에** 상대 담당자 확인이 있었는지 사용자에게 묻는다. 확인이 없으면 진행하지 않는다. 확인 방법(구두 합의 후 커밋 메시지 기록, 또는 PR)은 팀이 정한 것을 따른다 |

- 스펙 변경 커밋은 코드 커밋과 섞지 않는다. 메시지 접두어는 `spec:`. 구두 합의를 근거로 한 L2 변경은 메시지에 `<이름>와 구두 합의`를 남긴다.
- 공통 스펙(L1·L2)은 통합 브랜치에서 고친다. 현재 브랜치가 작업 브랜치면 사용자에게 알린다.
- 성공 기준을 고칠 때는 템플릿의 식별자 규칙을 지킨다 — 추가는 묶음 끝에 새 번호로, 삭제는 줄을 남기고 `(삭제 …)` 표시, 묶음 글자 재사용 금지. 번호를 다시 매기면 계획의 추적성 표·검증 보고·ADR이 가리키는 기준이 소리 없이 바뀐다.
- 스펙 티켓을 다시 열지 않는다. 요구사항 자체가 바뀌어 스펙을 사실상 다시 써야 하면 수정이 아니라 새 변경이므로, 새 스펙을 쓰고 옛 스펙은 `superseded`로 표시한다.

## status 전이

| 전이 | 누가 | 조건 |
|---|---|---|
| `draft` → `approved` | spec-writer | 위 승인 조건 충족 + 사용자 승인 |
| `approved` → `implemented` | spec-conformance-check | 전체 PASS |
| `approved`/`implemented` → `superseded` | 새 스펙을 쓰는 spec-writer | 새 스펙이 이 스펙의 계약이나 결정을 대체할 때. 옛 스펙 본문 첫 줄에 `대체: <새 spec_id>`를 적는다 |

`implemented` 스펙은 완료된 변경의 기록이므로 코드에 맞춰 고치지 않는다. 새 변경은 새 스펙으로 쓴다. `approved`만이 task-breakdown의 입력이다.

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "간단한 작업이라 스펙이 필요 없다" | 간단한 작업은 *긴* 스펙이 필요 없을 뿐이다. 성공 기준 두 줄짜리 스펙도 스펙이다. |
| "스펙은 코딩 후에 쓰면 된다" | 그것은 문서화지 스펙이 아니다. 스펙의 가치는 코드 *전에* 명확성을 강제하는 데 있다. |
| "어차피 요구사항은 바뀐다" | 그래서 스펙이 살아있는 문서다. 낡은 스펙도 스펙 없음보다 낫다. |
| "승인 기다릴 것 없이 계획까지 이어서 하자" | 스펙 반려 시 계획 작업이 전부 버려진다. 게이트는 기회비용 절감 장치다. |
| "계약은 양쪽 스펙에 다 적어두면 안전하다" | 두 곳에 적힌 계약은 반드시 어긋난다. 공통 스펙 한 곳에 쓰고 나머지는 참조한다. |
| "구현이 끝났으니 스펙을 코드에 맞춰 갱신하자" | 스펙은 변경 기록이지 현재 상태 문서가 아니다. 어긋남은 진행 중에 고쳤어야 하고, 완료된 스펙은 손대지 않는다. |

## 검증

종료 전 확인:

- [ ] spec-template.md를 읽고 frontmatter·목차·성공 기준 식별자(`§글자-번호`) 형식을 대조했는가
- [ ] 가정이 명시되고 사용자 확인을 받았는가
- [ ] 성공 기준이 묶음(§글자) 아래 `§글자-번호` 식별자를 갖고 구체적·검증 가능한가. 전역 순번(SC-N)으로 매기지 않았는가
- [ ] "확인한 사실과 가정"에서 확인값과 추정값이 구분됐는가 (임의 수치를 확정하지 않았는가)
- [ ] 제약과 경계(지켜야 할 조건/사용자 확인 필요/하지 않을 것)와 제외 범위가 정의됐는가
- [ ] 빈 필수 항목을 일반론으로 채우지 않고 "없음"으로 뒀는가
- [ ] scope를 정했는가. 애플리케이션 둘 이상인데 공통 스펙 없이 app 스펙만 쓰지 않았는가
- [ ] `parent`가 있으면 공통 스펙을 실제로 읽었고, 그 스펙이 `approved`인가
- [ ] `shared-app`이면 통합 브랜치에 저장했는가
- [ ] 승인된 스펙을 고쳤다면 등급(L0·L1·L2)을 판단했고, L1은 알림 필요를 보고했고, L2는 상대 확인을 먼저 받았는가
- [ ] `docs/spec/`에 draft로 저장하고 승인 요청 후 종료했는가 (계획·구현·TASK-N 작성 금지)
