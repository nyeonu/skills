# Spec Writer

코드 없이 추측으로 구현하는 것을 막는 스킬이다. 스펙은 사람과 에이전트가 공유하는 단일 진실 원본으로, 무엇을 왜 만들고 완료를 어떻게 판별하는지 정의한다. **이 스킬은 스펙 작성(Specify)까지만 수행하고 종료한다** — 계획 수립은 task-breakdown, 구현은 plan-executor의 몫이다. 이 경계를 넘지 마라.

addyosmani `spec-driven-development`의 Phase 1(Specify)을 이 워크플로우에 맞게 포크한 것이다.

## 사용 시점

- 새 기능·프로젝트·여러 파일에 걸친 변경을 시작할 때
- 외부 요구사항(기획서, 메신저, 이메일)을 구현 가능한 문서로 정리할 때
- 아키텍처 결정이 필요한 변경 전

**사용하지 않는 경우**: 한 줄 수정, 오타 교정, 요구사항이 자명하고 자기완결적인 변경. 요구사항이 모호하면(목표·성공 기준·제약·제외 범위 중 하나라도 한 문장으로 쓸 수 없으면) 이 스킬이 아니라 **interview-me부터** 시작한다.

## 작성 절차

### 1. 가정 표면화

스펙 내용을 쓰기 전에, 지금 하고 있는 가정을 명시하고 확인받는다:

```
내가 하고 있는 가정:
1. <요구사항에 대한 가정>
2. <아키텍처에 대한 가정>
3. <범위에 대한 가정>
→ 지금 정정해달라. 아니면 이대로 진행한다.
```

모호한 요구사항을 조용히 메꾸지 마라. 스펙의 존재 이유가 코드를 쓰기 *전에* 오해를 드러내는 것이다. **미확인 가정이 3개 이상 쌓이면 스펙 작성을 중단하고 interview-me로 전환한다.**

### 2. 코드베이스 확인

대상 코드베이스를 직접 탐색한다(Glob/Grep/Read). 기존 제약·컨벤션·아키텍처와 요구사항이 충돌하는 지점을 찾아 스펙에 반영한다. 충돌을 발견하면 어느 쪽이 우선인지 사용자에게 확인한다 — 충돌을 안고 쓴 스펙은 계획 단계에서 반드시 터진다.

### 3. 스펙 작성

모호한 지시는 검증 가능한 성공 기준으로 재구성한다:

```
요구사항: "대시보드를 빠르게 해달라"

재구성된 성공 기준:
- 대시보드 LCP < 2.5s (4G 기준)
- 초기 데이터 로드 < 500ms
→ 이 목표치가 맞는가?
```

템플릿:

```markdown
---
spec_id: <YYYY-MM-DD-브랜치명-주제-kebab-case>
title: <스펙 제목>
status: draft                # draft | approved | superseded
created: <YYYY-MM-DD>
---

# Spec: <기능/프로젝트 이름>

## 목표 (Objective)
<무엇을 왜 만드는가. 사용자는 누구이고 성공하면 무엇이 달라지는가.>

## 성공 기준 (Success Criteria)
<완료를 판별하는 구체적·검증 가능한 조건. 각 항목에 SC-1, SC-2… 형식의 ID를 붙인다.
이 ID는 task-breakdown의 추적성 매핑과 spec-conformance-check의 검증 단위가 된다.
가능하면 각 SC를 테스트로 옮길 수 있는 형태(주어진 상태/입력 → 기대 결과)로 쓴다 —
task-breakdown이 이 SC에서 테스트 케이스를 도출한다(tdd 스킬 출처 ①).>
- SC-1: <조건>
- SC-2: <조건>

## 배경 및 제약 (Context & Constraints)
<코드베이스에서 실제 확인한 기존 구조·컨벤션·기술 제약. 요구사항과의 충돌과 그 해소 결과.>

## 경계 (Boundaries)
- **항상 할 것**: <예: 커밋 전 테스트, 기존 네이밍 컨벤션 준수>
- **물어보고 할 것**: <예: DB 스키마 변경, 의존성 추가>
- **하지 말 것**: <예: 기존 API 시그니처 변경, 무관한 리팩토링>

## 제외 범위 (Out of Scope)
<이번에 명시적으로 하지 않는 것. 침묵된 비합의가 어긋남의 절반이다.>

## 미해결 질문 (Open Questions)
<사람의 입력이 필요한 미결 사항. 외부 요구사항이면 기획자에게 되물을 질문.>
```

### 4. 저장 및 승인 요청 — 여기서 종료

- `docs/spec/YYYY-MM-DD-<브랜치명>-<주제>.md`로 저장한다 (`status: draft`). 디렉터리가 없으면 생성한다. 브랜치명은 `git branch --show-current`로 확인하고, `/`가 포함되면 `-`로 치환한다 (예: `feature/login` → `feature-login`).
- 사용자에게 스펙 검토를 요청하고 **종료한다.** 승인 후의 작업 분해는 task-breakdown이 별도 세션에서 수행한다.
- 사용자가 승인하면 `status: approved`로 갱신한다. 이 승인이 첫 번째 게이트다.

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "간단한 작업이라 스펙이 필요 없다" | 간단한 작업은 *긴* 스펙이 필요 없을 뿐이다. 성공 기준 두 줄짜리 스펙도 스펙이다. |
| "스펙은 코딩 후에 쓰면 된다" | 그것은 문서화지 스펙이 아니다. 스펙의 가치는 코드 *전에* 명확성을 강제하는 데 있다. |
| "어차피 요구사항은 바뀐다" | 그래서 스펙이 살아있는 문서다. 낡은 스펙도 스펙 없음보다 낫다. |
| "승인 기다릴 것 없이 계획까지 이어서 하자" | 스펙 반려 시 계획 작업이 전부 버려진다. 게이트는 기회비용 절감 장치다. |

## 검증

종료 전 확인:

- [ ] 가정이 명시되고 사용자 확인을 받았는가
- [ ] 성공 기준이 SC-N ID를 갖고 구체적·검증 가능한가
- [ ] 코드베이스에서 실제 확인한 사실이 배경·제약에 반영됐는가
- [ ] 경계(항상/물어보고/하지 말 것)와 제외 범위가 정의됐는가
- [ ] `docs/spec/`에 draft로 저장하고 승인 요청 후 종료했는가 (계획·구현 진행 금지)
