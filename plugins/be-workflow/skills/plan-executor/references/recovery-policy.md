# 제한된 자동 복구

실패·blocked·미커버 분기·브리프 참조 실패가 생겼을 때만 읽는다. 최초 스펙·계획 승인과 조직의 더 엄격한 제한은 유지한다. 오케스트레이터는 진단과 계획 보정을 맡고, 코드 수정은 실행자에게 위임한다.

## 1. 원인과 권한

먼저 실패 명령·결정적 로그·관련 diff를 읽고 원인을 분류한다. 실패 로그만 보고 새 구현을 지시하지 않는다.

| 원인 | 처리 |
|---|---|
| 코드가 계획을 잘못 구현 | 현재 코드의 실패 부분만 수정 |
| 계획의 기술적 전제 오류 | 아래 허용 조건을 만족하면 보정 후 부분 수정 |
| 다른 병렬 작업의 빌드·환경 영향 | 해당 작성자와 순서 조정, 코드 수정 없이 제한된 재검증 |
| 승인된 기준에서 기대 결과가 명확한 테스트 누락 | 기준→테스트→작업 매핑에 추가한 뒤 테스트 작성·검증 위임 |
| 요구사항의 모호함·충돌, 권한 경계 밖 변경 | 해당 작업과 의존 작업을 멈추고 사용자에게 질문 |

**자동 보정은 모두 만족할 때만 허용한다.**
- 승인된 동작·범위·성공 기준·외부 API/이벤트 계약·권한/데이터 정책과 명시된 설계 제약을 그대로 유지한다.
- 원인과 영향받는 파일·작업을 증거로 한정할 수 있다. 예: 참조 오기, 산문으로 적힌 계약을 조립기가 읽는 선언으로 옮기는 표기 보정(원문에 있는 정보만, 재조립 뒤 브리프 포함 확인), 기존 테스트 프로파일의 누락된 빈 연결, 기존 승인 기준의 경계값 테스트.
- 운영 설정·새 의존성/버전·DB 스키마·배포·보안 설정을 바꾸지 않는다. 이 변경이 필요하면 사람에게 올린다.
- 기존 테스트를 삭제·skip·비활성화하거나 단언/기대값을 완화하지 않는다. 실제 인프라 검증을 mock으로 대체하지 않는다. 기대값의 오류 정정은 아래 조건을 모두 만족할 때만 오케스트레이터가 허용한다. 실행자는 스스로 기대값을 바꾸지 않는다.

**테스트 기대값 오류 정정**: 다음을 모두 기록하고 확인한다.
- 승인된 스펙·외부 계약의 원문이 수정 후 기대값을 명확히 정하거나, 해당 동작을 기존대로 보존하도록 정한다. 스펙의 침묵이나 해당 코드가 수정 제외라는 사실만으로 기존 동작 보존을 추론하지 않는다.
- 기존 동작 보존인 경우, 이번 작업 전 기준 커밋의 관련 코드와 그 기준에서의 실행 결과를 확인한다. 현재 구현의 출력만으로 기대값을 정하지 않는다. 기준 환경을 재현할 수 없거나 근거끼리 충돌하면 사용자에게 올린다.
- 승인된 성공 기준·실패 조건을 삭제하거나 넓히지 않는다. 요청 입력·인증 조건·상태/에러 코드·부수효과를 대조하고, 정확한 새 기대값으로 단언한다. 예: HTTP 200이어도 승인된 오류 응답이라면 오류 코드와 금지된 DB 변경이 없다는 조건까지 검증한다.
- 변경 전후 기대값, 승인 원문, 실행 증거(기존 동작 보존이면 기준 커밋 포함), 영향 테스트를 복구 기록에 남긴 뒤 원래 작업의 회차를 차감하고 계획·추적성 표를 먼저 갱신한다. 이후 실행자에게 테스트 수정과 재검증을 위임한다. 독립 스펙 검증과 코드리뷰는 그대로 수행한다.

실행자는 여전히 자의적으로 계획을 고치지 않는다. 오케스트레이터는 보정 전후·근거·유지되는 승인 기준을 `## 복구 기록`에 남기고, 해당 작업 블록·파일 목록·검증 명령·추적성 표 중 필요한 부분만 갱신한다. 스펙은 수정하지 않는다. 기존 승인을 새 요구사항의 승인으로 해석하지 않는다.

## 2. 보존과 회차

- 실패 시 전체 작업·파일을 초기화하지 않는다. 사용자 변경, 다른 실행자 변경, 검증된 완료 코드를 보존한다. 충돌할 파일의 실행자는 먼저 멈추거나 완료를 기다린다.
- **작업당 자동 복구 최대 2회**. 최초 구현 자체는 차감하지 않지만, 브리프 참조 실패 등 실행 전 발견한 계획 결함의 보정도 같은 예산에서 차감한다. 실패 후 수정 지시를 내리기 전에 회차를 기록한다. 계획만 보정하고 재조립하는 복구도 1회다. 진단을 위한 시험 수정도 회차에 포함한다.
- 한 회차는 한 원인 가설에 대한 제한된 수정과 검증이다. 검증이 실패하면 실행자는 보고하고 멈춘다. 한 지시 안에서 여러 수정·재실행 루프를 숨기지 않는다.
- 다음 회차는 로그·diff·실험 결과에서 얻은 **새 근거와 달라진 수정 가설**이 있을 때만 허용한다. 같은 오류와 같은 가설이면 잔여 회차가 있어도 중단한다.
- 회차는 원래 작업 ID에 누적한다. 계획 보정·작업 분리·실행자/모델 교체·세션 재개·전체 검증/후속 리뷰에서 같은 작업을 다시 고치는 경우에도 초기화하지 않는다. 여러 작업을 고치는 회차는 수정 대상 각각에 합산한다.
- 읽기 전용 진단은 수정 회차와 별개로 실패 건당 1차 조사와 그 결과에 따른 추가 조사 1회까지만 한다. 그 뒤에도 원인이나 허용 범위를 한정하지 못하면 사용자에게 올린다. 조사 명목의 무한 위임을 금지한다.
- 병렬 빌드 충돌·도구 잠금으로 코드를 바꾸지 않고 같은 명령을 재실행하는 것은 수정 회차가 아니다. 템플릿의 60초 간격·최대 5회 제한을 적용하고 이후에는 조정하거나 blocked로 보고한다. 새 에이전트로 기다림 횟수를 초기화하지 않는다.
- 영향 없는 완료 작업은 done을 유지한다. 공유 코드·환경이 바뀌어 검증이 무효가 된 완료 작업만 in_progress로 돌려 재검증한다. **재검증 대상이라는 이유만으로 코드를 재작성하지 않는다.**

### 환경 준비·도입 작업과 복구의 구분

- **환경 준비**: 승인된 명령·도구 버전·검증 범위를 그대로 실행하기 위한 준비만 별도 기록하고 차감하지 않는다. 예: 이미 설치된 승인 JDK를 JAVA_HOME으로 선택, 승인된 로컬 DB 기동, 사용자 VPN 연결 대기. 발견 시점이 아니라 변경 내용으로 판단한다. 새 버전 설치·코드/설정 파일 수정·검증 명령의 의미 변경은 이 예외가 아니다.
- 계획의 `## 환경 준비 기록`에 원인·조치·확인 결과·사용 횟수를 남긴다. 환경 문제별로 근거 있는 준비 조치 1회와 확인 1회만 자동 수행한다. 실패하면 재시도하지 말고 보고한다(병렬 충돌·잠금 대기는 위 별도 제한). 동일 원인의 이름·세션을 바꿔 한도를 초기화하지 않는다. 환경이 필요 없는 독립 작업은 계속한다. 연결 성공을 E2E 통과로 보고하지 않는다.
- **사전 위임된 기반 도입**: 승인 계획에 해당 기반 도입 목적, 변경 파일, 허용 보정 범위, 성공 기준이 명시된 작업의 최초 구현에만 `(추정)` 보정을 허용한다. 이 예외는 일반적인 설정 오류 시 blocked 규칙보다 우선하지만, 위 권한 경계·기대값 정정 조건을 면제하지 않는다. 승인된 도입 범위 안에서 구현 전 읽기 전용 확인으로 틀린 가정을 식별하고 구현할 수 있다.
- 결함 재현을 위한 수정 전 코드 검증이나 아직 구현하지 않은 동작의 의도된 실패는 원인이 확인되면 복구 실패로 세지 않는다. 이 확인은 선택이며 테스트 선행을 요구하지 않는다. 환경/기반의 기동·컴파일 실패 또는 수정된 코드의 검증 실패는 이 예외가 아니므로 실행자는 보고하고 멈춘다. 이후 수정은 도입 작업도 오케스트레이터가 집계하는 복구다. 최초 실행 안에 설정 수정·재시도 루프를 숨기지 않는다.
- 검증된 사전 위임 구현을 계획 2절에 사실대로 반영하는 것은 결과 기록으로 차감하지 않는다. 실패 뒤 후속 지시·파일 목록·검증 명령·체크포인트 순서·참조 조각을 바꾸는 것은 계획 보정으로 차감한다. 여러 보정을 하나로 묶을 수 있는 것은 같은 원인 가설·같은 수정 지시·같은 검증 회차일 때뿐이다.
- 공통 환경/전체 검증의 계획 보정은 원인을 도입한 작업에 귀속한다. 여러 작업의 지시를 고치면 각각 차감한다. 귀속할 작업이 없으면 계획에 고정 ID `PLAN`을 기록하고 동일한 최대 2회·새 근거·중단 규칙을 적용한다. 작업 한도를 소진한 실패를 PLAN으로 옮기지 않는다.

계획 끝에 다음 표를 둔다. 실행 전 행을 만들고 종료 후 결과를 채운다. 재개 시 표를 먼저 확인하며, 기록이 없어 이미 쓴 회차를 확인할 수 없으면 0회로 가정하지 말고 사용자에게 확인한다.

| 작업 | 회차/2 | 실패 증거·원인 | 새 근거·수정 가설 | 계획 보정 전→후·유지 기준 | 수정 파일·보존 대상 | 검증 명령·결과 | 실행자·다음 조치 |
|---|---|---|---|---|---|---|---|

임시 브리프 MD는 이 표의 대체물이 아니다. 로그 전문 대신 결정적인 출력과 필요한 로그 위치만 기록한다.

## 3. 부분 수정 지시

작은 수정이고 기존 문맥이 유효하면 기존 실행자를 이어 쓴다. 같은 오해의 반복·긴 불필요한 문맥·재개 불가일 때만 새 실행자를 쓴다. 모델 승격도 근거와 잔여 회차가 있어야 한다.

복구 지시에는 아래 슬롯만 필요한 만큼 채운다. 스펙·계획 전체를 재전송하지 않는다. 승인 기준·제약·계약은 필요한 원문을 그대로 인용한다.

- **새 실행자**: `executor-brief-template.md`의 Environment·Rules·Report format과 `../../testing-policy/references/testing-rules.md`의 **원문 전체**를 함께 전달한다. 작업 디렉터리·브랜치 슬롯은 실제 값으로 채운다. `{{TESTING_RULES}}` 자리표시자나 파일 경로만 전달하지 않는다. 실행자는 스킬을 별도로 로드하지 않으므로 공통 지침이 실제 복구 프롬프트에 포함됐는지 배정 전에 확인한다.
- **기존 실행자**: 최초 브리프의 공통 테스트 지침과 작업 범위 규칙이 계속 적용됨을 명시한다. 문맥을 유지하지 못하면 새 실행자 전달 절차를 따른다.

```text
Recovery: <plan_id / original task id / attempt N of 2>
Failure: <command and decisive output>
Evidence: <cause, prior attempt and result, new evidence>
Contract: <verbatim relevant acceptance criteria, constraints, interfaces>
Current state: <relevant paths, current diff, completed work to preserve>
Correction: <recorded plan correction, allowed files, exact scope; no restart>
Verify: <targeted commands and affected regression checks>
Stop: report after this correction and verification; do not start another repair loop
```

부분 수정으로 변경 파일을 늘릴 때도 먼저 오케스트레이터가 계획과 영향 범위를 갱신한다.

## 4. 검증과 중단

오케스트레이터가 관련 명령을 직접 실행하고 결과를 확인한다. 테스트 이름만 맞추지 말고 입력·단언·실제 인프라 사용이 승인 기준을 검증하는지 diff를 확인한다. 수정한 코드와 테스트가 함께 같은 오해를 공유하지 않도록 기준 원문과 대조한다.

수정 부분과 영향받는 회귀 검증을 먼저 실행한다. 변경 영향이 없고 코드·환경도 그대로인 완료 작업을 전부 재실행하지 않는다. 계획 완료 시 전체 검증, 이후 독립적인 스펙 적합성 검증·코드리뷰는 생략하지 않는다. 이미 적합성 검증·리뷰가 끝난 뒤 코드를 고쳤다면 기존 판정을 완료 증거로 재사용하지 않고 변경된 코드에 대해 다시 검증·리뷰한다.

한도 소진, 새 근거 없는 반복, 권한 경계 밖 변경이면 해당 작업을 blocked로 둔다. 의존 작업은 실행하지 않고, 영향 없는 독립 작업은 계속할 수 있다. 사용자에게 완료·보존한 결과, 실패 원인과 시도, 남은 문제, 필요한 결정만 보고한다. 통과한 것처럼 처리하지 않는다.
