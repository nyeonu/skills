# Plan Executor

task-breakdown이 작성하고 사용자가 승인한 계획 문서를 실행하는 스킬이다. 이 스킬을 실행하는 세션이 **오케스트레이터**(고비용 모델)이고, 작업 하나를 받아 수행하는 서브에이전트가 **실행자**(저비용 모델)다. 오케스트레이터는 직접 코드를 수정하지 않는다. 작업은 실행자에게 위임하고 순서 제어·검증·예외 대응만 담당한다. 이 분리가 비용 최적화의 핵심이다.

## 실행 절차

### 1. 계획 로드 및 승인 확인

- 대상 계획 문서를 읽는다. 계획은 `docs/<티켓 키>/plan.md`(에픽의 작업 plan은 `docs/<에픽 키>/<작업 티켓 키>/plan.md`)에 있다. 경로를 지정받지 않았으면 티켓 키를 묻고, 그것도 없으면 `docs/*/plan.md` 중 `status: approved`인 것을 찾아 사용자에게 확인받는다. `kind: epic`인 계획은 직접 실행 대상이 아니다 — 4절 "분할과 순서"에서 `depends_on`이 충족된 작업 plan을 골라 그것을 실행한다.
- frontmatter의 `status`가 `approved`가 아니면 실행하지 말고 사용자에게 승인 여부를 물어라. 사용자가 확인해주면 `status: approved`로 갱신 후 진행한다. 승인 게이트는 이 워크플로우에서 사람이 통제권을 유지하는 장치이므로 생략하지 않는다.
- 계획의 "선택한 방식과 이유"에 되돌리기 비싼 결정이 표시되어 있는데 대응하는 ADR(`docs/decisions/`, `Proposed`)이 없으면, 실행 전에 adr-writer로 작성할 것을 사용자에게 안내한다.
- **스펙 변경 감지**: frontmatter의 `spec_rev`와 현재 값(`git log -1 --format=%H -- <spec>`)을 비교한다.
  - 다르면 실행하지 않고 사용자에게 알린다 — 계획이 참조한 스펙 이후에 스펙이 바뀌었으므로, 변경 내용(`git diff <spec_rev>..HEAD -- <spec>`)을 보여주고 task-breakdown으로 계획을 재검토할지 확인받는다.
  - `spec_rev`가 없는 옛 계획은 경고만 하고 진행한다.
- **상위 계획 변경 감지**(작업 plan일 때): frontmatter에 `parent`가 있으면 `parent_rev`와 현재 값(`git log -1 --format=%H -- <parent>`)을 같은 방식으로 비교한다. 다르면 실행하지 않고 변경 내용을 보여준 뒤 재검토 여부를 확인받는다. 상위 계획의 `status`가 `approved` 또는 `in_progress`가 아니어도 실행하지 않는다.
- **브리프 재료는 스크립트가 뽑는다**: 계획은 목표·범위를 재서술하지 않으므로 Goal과 Do not touch는 스펙에서 온다. 추출·참조 해소·통계는 `references/assemble_brief.py`가 제목 기준으로 결정적으로 수행한다(2절 참고). 손으로 자르거나 줄 번호로 자르지 않는다. 계획에 "목표"·"범위" 절이 남아 있는 옛 계획(0.1.11 이전)은 스크립트 대신 그 절을 그대로 쓴다.
- 실행 시작 시 `status: in_progress`로 갱신한다.

### 2. 작업 디스패치

frontmatter의 `tasks` 목록을 기준으로 실행한다.

- `depends_on`이 모두 `done`인 작업만 시작할 수 있다. 서로 의존관계가 없는 작업들은 **같은 턴에 병렬로** 실행자를 띄운다.
- **대상 파일이 겹치는 작업은 의존관계가 없어도 병렬로 띄우지 않는다.** 병렬 후보들의 "대상 파일" 목록을 먼저 대조하고, 한 파일이라도 겹치면 그 작업들은 순서대로 실행한다. 실행자는 같은 작업 트리를 공유하므로, 한쪽이 파일을 되돌리거나 덮어쓰면 다른 쪽의 작업이 소리 없이 사라지고 검증은 엉뚱한 작업을 실패로 판정한다. 계획이 겹치는 작업을 병렬 가능하게 적어 두었다면 그것은 계획의 결함이므로 순차 실행 사실을 보고에 남긴다.
- 실행자의 모델은 작업의 frontmatter `tier` 필드를 현재 플랫폼의 모델로 매핑해 결정한다. 각 작업 = 실행자 1개.
  - tier는 플랫폼 중립 필드다 — Claude에서는 `standard` → sonnet, `light` → haiku로 매핑한다(다른 플랫폼에서 실행 중이면 그 플랫폼의 주력 모델/경량 모델로 매핑한다). 필드가 없으면 `standard`로 간주한다.
  - tier 지정은 플래너의 판단이므로 오케스트레이터가 임의로 바꾸지 않는다 — 단, light 작업이 재시도까지 실패했다면 재시도 시 standard로 올리는 것은 허용된다(그 사실을 보고에 포함하라).
- 실행자에게 계획 문서 전체나 스펙 전체를 넘기지 마라. 브리프는 **`references/assemble_brief.py`로 조립한다** — 손으로 조립하면 세션마다 형식·참조 셈법이 달라져 측정값을 비교할 수 없다. 작업마다 한 번 실행한다:
  ```bash
  python3 <skill>/references/assemble_brief.py --spec <spec.md> --plan <plan.md> --task T2 \
    --model sonnet --worktree "$PWD" --branch "$(git branch --show-current)" \
    --out docs/<티켓 키>/briefs/<plan_id>-T2-sonnet.md        # 작업 plan이면 --parent ../plan.md 추가, 재시도는 -retry1
  ```
  스크립트가 넣는 것: 환경 안내(워크트리·브랜치), 고정 규칙(`references/executor-brief-template.md`), Goal(스펙 1절의 첫 `###` 전까지 — 배경 소절은 실행자에게 불필요), Do not touch(스펙 2절 제외 + 6절), Shared design(아래), 작업 블록 전문, 보고 형식. 출력 파일을 실행자 프롬프트로 **그대로** 쓴다. 문장을 더하거나 빼지 않는다 — 더할 말이 있으면 계획을 고친다.
- **참조 해소는 스크립트가 하고, 판정은 오케스트레이터가 한다.** 스크립트는 작업 블록의 백틱 이름 중 명시 참조("2절 `X` 참조")와 타입형 이름(CamelCase, `Type.member`)을 계획 2절(및 `--parent` 2절)에서 찾아, 코드 블록은 `// <경로>` 주석 단위 조각으로, 표·불렛은 해당 줄만 Shared design에 넣는다. 첫 줄 통계에 `해소 실패 N`이 찍히고 종료 코드 2면 **실행자를 띄우지 않는다** — 명시 참조한 이름이 2절에 없는 계획 결함이므로 사용자에게 어느 작업의 어느 이름인지 보고하고 task-breakdown으로 고친 뒤 재개한다. 철자만 다른 이름(대소문자·접미사)도 같은 결함이다. 실행자가 모르는 이름을 받으면 추측으로 만들어 내고, 그 결과는 검증 단계에서 엉뚱한 실패로 나타난다.

**브리프 파일**: `--out`으로 저장된 `docs/<티켓 키>/briefs/<plan_id>-<T-id>-<모델>.md`가 실행 기록이다. 첫 줄 통계(`<!-- brief T2 sonnet · 줄 · 자 · 추정 토큰 · Shared design 참조 N(명시 M, 해소 실패 K) · 변경 파일 · 테스트 -->`)는 사용자 보고의 브리프 행에 그대로 옮긴다. 이 폴더는 커밋하지 않는다(`.gitignore`에 `docs/*/briefs/`).

**채널 언어 정책**: 오케스트레이터 ↔ 실행자 통신은 일회성이고 사람이 읽지 않으므로, 보일러플레이트(역할 규칙)와 보고 형식은 **영어 고정 계약**을 쓴다 — 토큰이 적게 들고 소형 모델의 지시 이행률이 높다. 단 두 가지는 예외다:

1. **스펙·계획 원문(Goal·제외 범위·작업 블록·참조한 공통 설계)은 번역·요약·압축 없이 한국어 그대로 인용한다** — 승인받은 문서와 실제 지시 사이에 번역이라는 해석 단계를 만들지 않는다.
2. **산출물(코드 주석, 문서, 커밋 대상 텍스트)과 사용자 보고는 저장소 언어(한국어)를 따른다** — 영어는 통신 채널에서만 쓴다.

보고는 자유 산문이 아니라 아래 고정 슬롯 형식만 허용한다 — 구조화는 토큰과 모호함을 동시에 줄이지만, 산문 압축(관사·접속사 생략)은 모호함을 늘리므로 금지다.

실행자 프롬프트는 `references/executor-brief-template.md`가 원본이고 스크립트가 채운다. 슬롯은 다섯이다 — `Goal`(스펙 1절), `Do not touch`(스펙 2절 제외·6절), `Shared design`(참조한 2절 항목, 없으면 슬롯 자체가 빠짐), `Your task`(작업 블록 전문), `Report format`(아래 고정 슬롯). 템플릿의 규칙에는 "계획이 지정한 테스트 지원·설정·빌드가 동작하지 않으면 우회하지 말고 되돌린 뒤 `blocked`로 보고한다"가 들어 있다 — 통과시키려고 설정을 고친 실행은 계획 결함을 숨긴다. 보고 형식:

```
files: <changed file paths, comma-separated>
verify: <command> → PASS | FAIL — <shortest decisive output line>
tests: <test file · test name, one per line | ->
uncovered: <branches/edge cases found but not covered by the plan | ->
blocked: <what stopped you and why | ->
notes: <only what the orchestrator must know to proceed | ->
```

### 3. 검증

실행자의 "완료" 보고를 그대로 믿지 마라. 저비용 모델은 실패를 성공으로 보고하는 경우가 있다.

- 보고가 계약 형식(위 Report format)을 지키지 않았거나 필수 슬롯이 비어 있으면, 내용을 추측으로 메꾸지 말고 형식 위반으로 재요청한다. `blocked`가 채워져 있으면 verify 전에 그 사유부터 처리한다.
- 작업의 verify 명령을 오케스트레이터가 직접 실행해 확인한다. 실행자 보고의 `verify` 슬롯은 참고일 뿐 증거가 아니다. 테스트 기반 verify는 통과 여부만이 아니라 **skip·비활성화된 테스트가 없는지, 계획에 명시된 테스트(보고의 `tests` 슬롯과 대조)가 실제로 존재하는지**도 확인한다 — 테스트를 지우거나 약화시켜 만든 그린은 실패다.
- 통과: frontmatter의 해당 작업 `status: done`으로 갱신하고 다음 작업으로.
- 실패: 실패 로그를 포함해 같은 작업을 새 실행자로 1회 재시도한다. 재시도도 실패하면 작업을 `blocked`로 표시하고 사용자에게 상황을 보고한 뒤 지시를 기다린다. 의존 작업이 없는 다른 작업은 계속 진행해도 된다.

### 4. 완료 처리

- 모든 작업이 `done`이면 계획 문서의 "전체 검증" 절차를 직접 실행한다.
- 통과하면 계획 `status: done`으로 갱신하고 아래 5번 형식으로 사용자에게 보고한다.
- 작업 plan(`parent`가 있음)이면 상위 에픽 plan의 `work_plans`에서 이 작업 plan을 `status: done`으로 갱신하고, 상위 `status`가 `approved`면 `in_progress`로 올린다. 에픽의 모든 `work_plans`가 `done`이면 에픽 plan의 "전체 검증" 절차를 실행하고 통과 시 에픽 `status: done`으로 갱신한다. 작업 plan 하나가 끝났다고 에픽 전체 검증을 돌리지 않는다.
- ADR 처리 (2시점 구조의 두 번째 시점 준비):
  - 실행 중 결정이 계획과 다르게 변경됐다면, adr-writer로 새 ADR을 작성해 기존 ADR을 대체(supersede)하도록 사용자에게 제안한다.
  - 계획에 연결된 `Proposed` ADR의 `Accepted` 확정은 **스펙 적합성 검증 통과 후** 수행함을 보고에 명시한다. 오케스트레이터가 임의로 확정하지 않는다.
  - 계획에 표시되지 않았던 되돌리기 비싼 결정이 실행 중 새로 발생했다면 adr-writer로 ADR 작성을 제안한다.
- 전체 검증이 실패하면 원인으로 추정되는 작업을 특정해 사용자에게 보고한다. 임의로 대규모 수정을 하지 마라.

### 5. 사용자 보고

**사용자 보고는 한국어 산출물이다** (채널 언어 정책의 예외 아님 — 원칙 그대로다). 결과부터 쓴다 — 과정 서술은 판정에 필요한 만큼만 남긴다. 필수 항목에 쓸 내용이 없으면 일반론으로 채우지 말고 `없음`이라고 쓴다.

테스트 대조는 새 판단을 만드는 단계가 아니다 — **계획의 추적성 표(기준 → 테스트 → 작업)를 기준선으로, 실제 테스트 코드·실행 결과를 기계적으로 대조**한다. 기준선 없는 커버리지 판정(라인 % 등)으로 대체하지 않는다.

- 재료는 실행자 보고의 `tests`·`uncovered` 슬롯 취합 + 오케스트레이터가 직접 실행한 verify 결과다.
- 대조 후 실제 테스트 이름이 계획 표와 다르면 **계획 표를 실제 이름으로 갱신한다** — 이 표는 기준 ↔ 테스트의 단일 색인이라 낡으면 spec-conformance-check의 추적성 판정이 무너진다.
- 테스트 이름은 기준 식별자 없이 무엇을 검증하는지 서술해야 하므로(tdd 스킬), 실행자가 식별자나 번호 접두어를 붙였거나 이름이 무엇을 검증하는지 불명확하면 대조 표의 결과 열에 결함으로 적는다.

```markdown
## 실행 결과

- 계획: <계획 문서 경로>
- 완료한 작업: <완료 T-N 목록 / 전체 개수. 재시도나 tier 상향이 있었으면 함께 적는다>
- 브리프: <작업별 한 줄 — 브리프 파일 첫 줄 통계 + `결과(1회차 PASS | 재시도 n회 | 승격 | blocked)` + `계획 이탈(없음 | 내용)`. 계획 이탈은 PASS와 별도로 적는다 — 통과했어도 계획이 지정한 것을 바꿨으면 이탈이다>
- 바뀐 파일: <경로 목록>
- 판정: <전체 검증 통과 여부>

## 검증

| 검증 항목 | 실행한 명령 | 결과 |
|---|---|---|
| T1 검증 | npm test -- src/auth | PASS |
| 전체 검증 | npm test | PASS |

## 테스트 대조

| 계획한 테스트 (출처/층) | 스펙 기준 | 실제 테스트 (파일 · 테스트 이름) | 결과 |
|---|---|---|---|

## 다음 단계
```

- "다음 단계"는 생략하지 않는다. 여기서의 검증은 "계획대로 됐는가"까지이며, "스펙에 맞는가"는 별도 단계다.
- 테스트 대조 표에 **미작성이 있으면 완료가 아니다** — 해당 작업의 완료 기준 미충족이므로 3번 검증의 재시도 절차로 되돌린다.
- "미커버 분기"는 실행 단계에서 보충하지 않는다. 사용자에게 보고하고, 사용자가 확인하면 task-breakdown으로 보충 계획을 만든다(계획 변경 규칙과 동일). 여기서 임의로 테스트를 추가하면 어떤 테스트를 만들지의 판단이 승인 게이트를 우회한다.

## 타협 금지 (Anti-Rationalization)

실행이 길어질수록 "이 정도면 되겠지"라는 타협이 생긴다. 아래 변명이 떠오르면 절차를 건너뛰고 있다는 경고다.

| 떠오르는 변명 | 실제 |
|---|---|
| "실행자가 완료했다고 하니 됐다" | 저비용 모델은 실패를 성공으로 보고한다. verify를 직접 실행하기 전까지 완료가 아니다. |
| "테스트가 대부분 통과하니 넘어가자" | 실패한 테스트 1개가 곧 미완료다. 통과율은 완료 기준이 아니다. |
| "실행자가 테스트를 조금 고쳐서 통과시켰다니 됐다" | 단언 완화·skip으로 만든 그린은 실패를 감춘 것이다. 계획의 테스트 명세와 대조하라. |
| "verify가 다 통과했으니 테스트 대조는 생략하자" | "테스트가 돌았다"와 "계획한 테스트가 전부 존재하고 통과했다"는 다른 명제다. 대조표 없는 완료 보고는 누락을 숨긴다. |
| "실행자 보고가 영어니 사용자 보고에 그대로 붙이자" | 채널 언어와 산출물 언어는 다르다. 사용자 보고·테스트 대조·문서는 한국어 산출물이다 — 영어는 일회성 통신에만 쓴다. |
| "작업 지시도 영어로 번역하면 토큰이 더 준다" | 계획 원문은 사용자가 승인한 것이다. 번역은 승인받지 않은 해석 단계를 끼워 넣는 새 오류원이다 — 원문 그대로 인용하라. |
| "두 작업이 같은 파일을 건드리지만 다른 부분이니 병렬로 돌리자" | 실행자는 파일 단위로 읽고 쓰며, 다른 쪽의 변경을 낡은 상태로 보고 되돌릴 수 있다. 겹치면 순차다. |
| "이 작은 수정은 내가 직접 하는 게 빠르다" | 한 번 직접 수정하면 다음에도 하게 되고, 비용 구조와 계획-실제 정합성이 무너진다. 위임하라. |
| "계획이 좀 이상하지만 대충 맞춰서 진행하자" | 계획과 현실이 어긋나면 멈추고 사용자에게 보고하는 것이 규칙이다. 임의 해석은 승인받지 않은 작업이다. |
| "작업이 많이 남았으니 검증은 마지막에 몰아서 하자" | 검증 없이 쌓인 작업은 실패 원인을 찾을 수 없게 만든다. 작업마다 즉시 검증한다. |
| "전체 검증은 개별 verify가 다 통과했으니 생략하자" | 개별 통과가 통합 동작을 보장하지 않는다. 전체 검증은 별개 단계다. |
| "전체 검증까지 통과했으니 스펙도 충족했을 것이다" | 전체 검증은 계획 기준이다. 계획이 스펙을 잘못 번역했을 가능성은 spec-conformance-check가 잡는다. |

## 오케스트레이터가 지켜야 할 것

- **직접 구현 금지**: 사소한 수정이라도 실행자에게 위임하라. 예외는 frontmatter 상태 갱신과 검증 명령 실행뿐이다. 오케스트레이터가 구현을 시작하면 비용 구조가 무너지고, 계획 문서와 실제 작업 내역이 어긋난다.
- **계획 변경 금지**: 실행 중 계획이 잘못됐다고 판단되면 실행을 멈추고 사용자에게 수정안을 제안하라. 계획 수정은 사용자 승인 후 task-breakdown으로 한다.
- **상태는 문서에 기록**: 진행 상황의 유일한 원본은 계획 문서의 frontmatter다. 세션이 끊겨도 문서만 보면 이어서 실행할 수 있어야 한다.
