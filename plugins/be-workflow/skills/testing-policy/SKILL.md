# Testing Policy

테스트 수나 작성 순서가 아니라 요구한 동작을 검증하는지 판단한다.
TDD를 선택할 수 있지만 기본값으로 강제하지 않는다. 사용자가 명시한 순서가 있으면 따른다.
먼저 [공통 테스트 지침](references/testing-rules.md)을 읽고 적용한다.
그 파일이 공통 규칙의 단일 원본이며, 실행자 브리프에도 원문 그대로 삽입된다.

## 적용 위치

- **계획 단계**: task-breakdown이 아래 도출 관점으로 테스트 기준선과 테스트 수준을 정한다.
- **실행 단계**: 실행자는 브리프에 포함된 공통 지침과 작업별 기준으로 테스트를 작성·실행한다.
- **완료 단계**: plan-executor는 실제 단언·실행 결과를 기준선과 대조한다. 스펙 적합성 검증과 코드 리뷰는 별도로 수행한다.
- **계획 없는 소규모 수정**: 이 스킬을 직접 사용한다. 별도 계획 문서 없이 변경 동작·검증·남은 공백을 보고한다.

## 저장소 확인

기존 테스트와 프로젝트 규칙, 빌드 래퍼, README·CI에서 테스트 위치·관례와 실제 실행 명령을 확인한다.
관련 테스트 실행과 전체 검증 명령을 구분한다. `npm test` 같은 기본값을 가정하지 않는다.

## 테스트 케이스 도출 — 5출처

기존 테스트로 충분한 항목은 재사용하고, 빠진 동작을 검증할 케이스를 선택한다.
각 케이스는 출처·입력 또는 상태·기대 결과·수준(유닛/통합/E2E)을 설명할 수 있어야 한다.
모든 출처에서 새 테스트를 만들거나 모든 조건 조합을 열거할 필요는 없다.

| 출처 | 확인할 내용 |
|---|---|
| ① 스펙 성공 기준 | 변경한 기능의 관찰 가능한 결과와 주요 계산·판정 규칙. 기준 하나당 새 테스트 하나를 만들지 않고, 기존 테스트와의 대응도 기록한다. |
| ② 동등 분할·경계값 | 결과가 달라지는 입력 묶음의 대표값과 관련 경계값. 복합 조건은 의미 있는 조합을 선택한다. |
| ③ 오류 분기 | 권한 거부·잘못된 입력·의존성 실패처럼 관찰 가능한 결과가 달라지는 경로. 모든 내부 if문을 테스트로 고정하지 않는다. |
| ④ 상태·순서 | 변경과 관련된 상태 전이·멱등성·동시성·실패 시 복원. 무관한 항목은 추가하지 않는다. |
| ⑤ 과거 버그 | 해당 결함을 구별하는 회귀 테스트. 가능하면 수정 전 코드에서도 실행해 결함 검출을 확인한다. |

5출처 밖의 근거는 `기타: <발견 근거>`로 기록한다.
예상 결과가 요구사항에서 정해지지 않으면 임의로 만들지 않고 불확실성을 보고한다.
계획은 초기 기준선이다. 구현 중 발견한 누락은 실행자가 `uncovered`로 보고하고,
오케스트레이터가 기존 요구사항·변경 범위 안에서 보완을 위임한다. 새 업무 규칙은 사용자에게 확인한다.

## 수준·구조 선택

- 계산·변환·판정은 값과 결과를 검증하는 유닛 테스트부터 검토한다.
- DB 저장·트랜잭션·캐시·외부 계약 등 연결 자체가 검증 대상이면 필요한 통합 테스트를 둔다.
- 전체 사용자 경로로만 확인할 수 있는 핵심 동작은 E2E로 검증한다.
- 테스트 대역은 외부 경계를 통제할 때 사용한다. 실제 연결 동작을 검증했다고 보고하지 않는다.
- 판정과 무관한 IO 대역이 많이 필요하면 로직과 IO의 결합을 확인한다. 구조 변경은 승인 범위와 기존 관례를 따른다. 파이프라인의 구체적 배치는 task-breakdown의 `references/structure-rules.md`에서 정한다.

## 전달과 완료

테스트 이름은 대상 동작·조건·기대 결과를 드러낸다. 식별자나 번호를 이름에 붙이지 않는다.
계획이 있으면 기준 ↔ 테스트 ↔ 작업의 연결은 추적성 표에 유지한다. 추가·개명 시 표도 갱신한다.
보고에는 실제 테스트 파일·이름, 실행 명령·결과, 미검증 항목과 이유를 남긴다.
순서 자유는 필요한 테스트 생략이나 검증 없는 완료를 허용한다는 뜻이 아니다.
