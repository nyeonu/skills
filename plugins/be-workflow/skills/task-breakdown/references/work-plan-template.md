# 작업 plan 템플릿 (에픽 하위)

에픽 plan(`plan-template.md`, `kind: epic`)이 승인된 뒤, 4절 "분할과 순서"의 작업 plan 하나마다
이 문서를 하나 쓴다. 작업 plan 하나는 브랜치·PR 하나이고, 한 에이전트 세션이 끝낼 수 있는
크기(작업 T 2~4개, 파일 1~5개씩)다. 승인은 작업 plan마다 받는다.

**상위를 재서술하지 않는다.** 선택 이유·공통 설계·추적성 표·분할 순서는 에픽 plan 소유이고,
목표·범위·성공 기준은 스펙 소유다. 이 문서는 자기 작업의 상세만 적는다. 상위가 바뀌면
`parent_rev`·`spec_rev`로 감지되어 실행이 멈춘다.

## 목차

- 템플릿 — frontmatter, 1 맡는 기준, 2 실행에 필요한 현재 상태, 3 작업(작업 블록 반복), 4 검증, 5 롤백
- 작업 블록 — 단일 티켓 plan의 4절에서도 같은 형식을 쓴다
- 작성 시 체크리스트

## 템플릿

````markdown
---
plan_id: <TASK-TICKET>              # 폴더명이자 에픽 plan work_plans의 id
title: <작업 plan 제목>
status: draft                        # draft | approved | in_progress | done
author: <작성 에이전트/사람>
created: <YYYY-MM-DD>
parent: ../plan.md                   # 에픽 plan. 이 파일은 docs/<에픽 키>/<작업 티켓 키>/plan.md에 있다
parent_rev: <에픽 plan 파일의 최신 커밋 해시>   # git log -1 --format=%H -- <parent>. 실행 전 상위 변경 감지용
spec: ../spec.md                     # 에픽 폴더의 스펙
spec_rev: <스펙 파일의 최신 커밋 해시>
branch: <작업 브랜치>                 # 예: feature/TASK-TICKET-<slug>
tasks:                               # 3절 작업 블록과 1:1 대응
  - id: T1
    title: <작업 제목>
    depends_on: []
    status: pending                  # pending | in_progress | done | blocked
    tier: standard                   # standard | light
---

# <작업 plan 제목>

## 1. 맡는 기준

<에픽 plan 추적성 표에서 이 작업 plan이 충족 위치인 행만 그대로 옮긴다. 문장을 고치지 않는다.
기준을 추가·삭제해야 하면 에픽 plan을 먼저 고친다.>

| 스펙 기준 | 테스트 이름 (출처/층) | 충족 위치 |
|---|---|---|
| <에픽 표의 문장 그대로> | <에픽 표의 이름 그대로> | T1 완료 기준 |

## 2. 실행에 필요한 현재 상태

<이 작업 plan이 건드릴 파일·함수·클래스의 현황과 기존 컨벤션. 실제로 확인한 사실만.
에픽 plan 2절 "관여하는 매직" 중 이 작업에 해당하는 것은 이름으로 가리킨다.>

## 3. 작업

### T1: <작업 제목>

<아래 "작업 블록" 형식>

### T2: <작업 제목>

<동일 구조 반복. depends_on이 있으면 첫 줄에 "T1 완료 후 시작" 명시.>

## 4. 검증

<이 작업 plan(PR 하나) 범위의 통합 확인 방법. 실행 가능한 명령. 에픽 전체 검증은 에픽 plan 5절.>

## 5. 롤백

<이 PR을 되돌리는 방법. 데이터·설정을 건드렸으면 그 되돌리기. 없으면 `없음`.>
````

## 작업 블록

작업 T 하나의 형식이다. 작업 plan 3절과 단일 티켓 plan 4절에서 같은 형식을 쓴다.
산문으로 구현 단계를 서술하지 않는다 — 표·코드 블록·수도코드로 적고, 산문은 주의사항에만 쓴다.

````markdown
### T1: <작업 제목>          <!-- "### T<n>:" 제목과 아래 변경 파일 표·테스트 불렛 형식은 assemble_brief.py가 읽는다 -->

- **변경 파일**

  | 파일 | 신규/수정 | 변경 요지 |
  |---|---|---|
  | `<경로>` | 수정 | <한 줄> |

- **인터페이스**: <에픽(또는 단일 plan) 2절 "인터페이스"에 있으면 그 이름을 2절과 같은 철자로
  백틱에 감싸 적는다 (예: "2절 `RefundNotificationDto` 참조"). plan-executor가 이 이름으로 2절을 찾아
  실행자 브리프에 넣는다 — 2절에 없는 이름은 실행이 멈춘다. 이 작업에서만 쓰는 시그니처·DTO·포맷이면
  여기 코드 블록으로 적는다. 구현 본문은 적지 않는다.>

  ```<언어>
  <이 작업 고유 시그니처 · DTO · 포맷>
  ```

- **결정 로직**: <유닛 테스트가 배정된 판정·상태 전이·규칙만 수도코드로. 함수 위치는
  2절 "결정 로직 위치"를 따른다. Repository·HTTP 호출 같은 IO 배관은 수도코드로 쓰지 않는다 —
  배관은 "변경 파일"의 변경 요지와 인터페이스로 충분하다. 결정 로직이 없는 작업이면 `없음`.>

  ```
  <입력> → <분기 조건> → <결과>
  ```

- **작성할 테스트**: <추적성 표에서 이 작업에 배정된 테스트 이름 목록. 구현 작업이면
  "이 테스트를 먼저 작성해 실패를 확인한 뒤(RED) 구현한다(GREEN)"가 기본 순서다.
  테스트 작성이 별도 작업으로 분리된 경우 이 항목은 그 작업에만 둔다.>
- **완료 기준**:
  - <검증 가능한 조건. 원칙은 "위 테스트가 통과한다">
- **검증 방법**:
  ```bash
  <실행 가능한 명령. 예: ./gradlew :application:test --tests "...">
  ```
- **주의사항**: <산문이 허용되는 유일한 자리. 하지 말 것, 함정, 엣지 케이스, 이 작업의 결정에
  관여하는 매직 한 줄. 테스트 skip·단언 완화로 통과시키는 것 금지. 인터페이스가 기존 코드와
  충돌하면 바꾸지 말고 멈춰 보고한다.>
````

## 작성 시 체크리스트

- [ ] `plan_id`가 에픽 plan `work_plans`의 id와 같고, `parent`·`parent_rev`·`spec`·`spec_rev`가 채워졌는가
- [ ] 1절이 에픽 추적성 표의 해당 행을 문장 그대로 옮겼는가 (추가·수정 없음)
- [ ] 선택 이유·공통 설계·분할 순서·목표·범위를 옮겨 적지 않았는가 (상위는 링크·이름 참조만)
- [ ] frontmatter `tasks`와 3절 `### T*`가 1:1 대응하는가
- [ ] 작업 블록마다 변경 파일 표가 있고 모든 경로를 실제로 확인했는가
- [ ] 인터페이스가 코드 블록이고, 상위 2절에 있는 것은 이름만 참조했는가
- [ ] 작업 블록이 백틱으로 참조하는 이름이 상위 2절(인터페이스·결정 로직 위치·관여하는 매직)에 같은 철자로 전부 있는가
- [ ] 결정 로직 수도코드가 IO 없는 함수 범위에 한정됐고, 배관을 수도코드로 쓰지 않았는가
- [ ] 산문이 주의사항에만 있는가
- [ ] `depends_on`이 없는 작업끼리 변경 파일이 겹치지 않는가
- [ ] 각 작업의 검증 방법이 실행 가능한 명령이고 tier가 지정됐는가
- [ ] 코드베이스를 처음 보는 에이전트가 이 문서와 상위 2절·스펙만으로 작업 가능한가
