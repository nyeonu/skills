# PLAN.md 템플릿

아래 구조를 그대로 사용한다. `<>` 부분만 채우고 섹션 구조와 순서는 유지하라.
frontmatter는 기계 파싱용이므로 유효한 YAML이어야 하고, 필드 이름과 값 형식을 바꾸지 않는다.
본문 문장과 분량은 작업에 맞게 조절한다. 필수 항목에 쓸 내용이 없으면 일반론으로 채우지 말고 `없음`이라고 쓴다.

```markdown
---
plan_id: <kebab-case-id>            # 예: 2026-07-06-session-token-refresh
title: <계획 제목>
status: draft                        # draft | approved | in_progress | done
author: <작성 에이전트/사람>
created: <YYYY-MM-DD>
target: <대상 저장소 또는 디렉터리>
spec: <원본 스펙 문서 경로>            # 예: docs/spec/2026-07-06-session-token-refresh.md
spec_rev: <스펙 파일의 최신 커밋 해시>   # git log -1 --format=%H -- <spec>. 실행 전 스펙 변경 감지용
parent_spec: <공통 스펙 위치>           # 스펙에 parent가 있을 때만. 예: fanclub-auth@feature/ASD-2141:docs/spec/...
parent_spec_rev: <공통 스펙 커밋 해시>   # 위와 같을 때만. 없으면 두 줄 모두 지운다
tasks:                               # 본문 작업 섹션과 1:1 대응
  - id: T1
    title: <작업 제목>
    depends_on: []                   # 예: [T1, T2]
    status: pending                  # pending | in_progress | done | blocked
    tier: standard                   # standard(기본) | light — 작업 성격 기반 실행 등급
                                     # standard: 판단·추론이 필요한 작업 / light: 명세가 완전한 기계적 작업
                                     # 실제 모델 매핑은 실행 플랫폼이 결정 (플랫폼 중립 필드)
  - id: T2
    title: <작업 제목>
    depends_on: [T1]
    status: pending
    tier: light
---

# <계획 제목>

## 1. 목표

<이 작업이 왜 필요한지, 완료되면 무엇이 달라지는지 1~3문장.
실행자가 모호한 상황에서 판단할 때의 기준이 된다.
스펙 내용을 그대로 반복하지 않는다 — 실행에 필요한 만큼만 가져온다.>

## 2. 실행에 필요한 현재 상태

<실행자가 알아야 할 코드베이스 현황. 관련 파일 경로, 핵심 함수/클래스,
기존 컨벤션, 관련 이슈/PR 링크. 실제로 확인한 사실만 쓴다.>

## 3. 선택한 방식과 이유

<왜 이 접근을 선택했는지 문장으로 설명한다. 사용자가 이 계획을 승인할지
판단하는 근거가 된다. 실제로 검토한 대안만 적는다 — 검토하지 않았다면
형식을 채우기 위해 대안을 만들어내지 않는다. 감수한 트레이드오프를 함께 쓴다.
되돌리기 비싼 결정이 포함되면 여기에 표시한다 — 승인 직후 adr-writer로
ADR Proposed 작성 대상이다.>

## 4. 범위

**포함:**
- <이번 계획에서 하는 것>

**제외 (하지 말 것):**
- <건드리지 말아야 할 것. 예: "기존 API 시그니처 변경 금지", "리팩토링 금지">

## 5. 추적성

<스펙의 성공 기준(SC-N) 각각이 어떤 테스트 케이스로 검증되고, 그 테스트가 어느
작업에서 작성·통과되는지 매핑한다 (SC → 테스트 케이스 → 작업). 모든 SC가
커버되어야 한다. 테스트 케이스는 tdd 스킬의 5출처를 기본 도출 경로로 하며,
출처와 층(유닛/통합/E2E)을 표시한다. 5출처 밖 테스트는 출처를
`기타: <발견 근거>` 형식으로 기록한다. 테스트로 표현할 수 없는 SC는
테스트 케이스를 "—"로 두고 사유를 적는다.>

| 스펙 기준 | 테스트 케이스 (출처/층) | 충족 위치 |
|---|---|---|
| SC-1 | "만료 토큰으로 요청 시 401" (①/통합) | T1 완료 기준 |
| SC-2 | "birthYear 1900 미만이면 400" (②/유닛) | T3 완료 기준 |
| SC-3 | — (문서 일치 조건, 사유: 실행 불가) | 전체 검증 항목 N |

## 6. 작업

### T1: <작업 제목>

- **대상 파일**: `<경로>` (실재하는 경로만)
- **작성할 테스트**: <추적성 표에서 이 작업에 배정된 테스트 케이스 목록.
  구현 작업이면 "이 테스트를 먼저 작성해 실패를 확인한 뒤(RED) 구현한다(GREEN)"가
  기본 순서다. 테스트 작성이 별도 작업으로 분리된 경우 이 항목은 그 작업에만 둔다.>
- **작업 내용**: <무엇을 어떻게 구현할지 단계별로. 사용할 기존 함수/패턴 명시.>
- **완료 기준**:
  - <검증 가능한 조건. 원칙은 "위 테스트가 통과한다". 예: "만료 토큰으로 요청 시 401 반환 테스트 통과">
- **검증 방법**:
  ```bash
  <실행 가능한 명령. 예: npm test -- src/auth>
  ```
- **주의사항**: <함정, 엣지 케이스, 하지 말 것. 테스트 skip·단언 완화로 통과시키는 것 금지.>

## 작성 시 체크리스트

- [ ] frontmatter `tasks`와 본문 `### T*` 섹션이 1:1 대응하는가
- [ ] frontmatter `spec`이 승인된 스펙 문서를 가리키고 `spec_rev`가 그 파일의 현재 커밋 해시인가 (parent가 있으면 `parent_spec`·`parent_spec_rev`도)
- [ ] 추적성 표가 스펙의 모든 SC-N을 커버하는가 (SC → 테스트 케이스 → 작업)
- [ ] 테스트 케이스마다 출처와 층(유닛/통합/E2E)이 표시됐는가
      - 기본 출처는 ①~⑤를 사용한다.
      - 5출처 밖 테스트는 `기타: <발견 근거>` 형식으로 무엇을 왜 검증하는지 기록한다.
- [ ] 실제 인프라가 필요한 동작(롤백·캐시 무효화 등)이 통합 테스트로 배정됐는가
- [ ] 모든 파일 경로를 실제로 확인했는가
- [ ] 각 작업의 검증 방법이 실행 가능한 명령인가
- [ ] 작업이 수직 슬라이스(기능 경로 단위)로 나뉘었는가
- [ ] 고위험 작업이 앞에 배치됐는가
- [ ] 제외 범위(하지 말 것)를 명시했는가
- [ ] "선택한 방식과 이유"에 실제로 검토한 대안과 트레이드오프만 기록했는가 (되돌리기 비싼 결정 표시 포함)
- [ ] 스펙 내용을 그대로 반복하지 않고 실행에 필요한 부분만 가져왔는가
- [ ] 빈 필수 항목을 일반론으로 채우지 않고 "없음"으로 뒀는가
- [ ] 각 작업에 tier를 지정했는가 (light로 내린 작업은 근거가 있는가)
- [ ] 저장 경로가 `docs/plan/YYYY-MM-DD-<브랜치명>-<주제>.md` 형식인가
- [ ] 코드베이스를 처음 보는 에이전트가 이 문서만으로 작업 가능한가
