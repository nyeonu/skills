# PLAN.md 템플릿 (단일 티켓 · 에픽 공용)

아래 구조를 그대로 사용한다. `<>` 부분만 채우고 섹션 구조와 순서는 유지하라.
frontmatter는 기계 파싱용이므로 유효한 YAML이어야 하고, 필드 이름과 값 형식을 바꾸지 않는다.
본문 문장과 분량은 작업에 맞게 조절한다. 필수 항목에 쓸 내용이 없으면 일반론으로 채우지 말고 `없음`이라고 쓴다. 단, 실행 기록 표는 작성 시 빈 표로 둔다.

이 템플릿은 두 가지로 쓴다. `kind`로 구분한다.

- **단일 티켓(`kind: single`)**: 이 문서 하나가 계획 전부다. 4절에 작업 블록(`work-plan-template.md`의 "작업 블록")을 직접 둔다.
- **에픽(`kind: epic`)**: 상위 계획이다. 4절에는 작업 plan 목록과 순서만 두고, 작업 상세는 하위 작업 plan(`work-plan-template.md`)에 둔다. 승인된 뒤 작업 plan을 쓴다.

**스펙을 재서술하지 않는다.** 목표·범위·성공 기준·전제가 틀릴 위험은 스펙 소유이고 frontmatter `spec`이 가리킨다. 실행자 브리프의 목표와 금지 범위는 plan-executor가 스펙 1절(한눈에 보기)·2절(제외)·6절(하지 않을 것)에서 직접 가져온다. 계획은 스펙에 없는 것만 적는다 — 어떻게 만들지, 어떤 테스트로 어느 기준을 덮는지, 어떤 순서로 나누는지.

## 목차

- 템플릿 — frontmatter(기계 파싱 필드), 1 선택한 방식과 이유, 2 공통 설계, 3 추적성, 4 분할과 순서(에픽) / 작업(단일), 5 전체 검증, 6 위험과 롤백
- 복구 기록·환경 준비 기록 — 실행 시 오케스트레이터가 갱신
- 작성 시 체크리스트

## 템플릿

````markdown
---
plan_id: <티켓 키>                  # 폴더명과 같게. 단일: 티켓 키, 에픽: 에픽 키
title: <계획 제목>
kind: single                         # single | epic
status: draft                        # draft | approved | in_progress | done. 에픽은 work_plans가 전부 done일 때 done
author: <작성 에이전트/사람>
created: <YYYY-MM-DD>
target: <대상 저장소 또는 디렉터리>
spec: spec.md                        # 같은 폴더의 스펙. 다른 위치면 그 경로
spec_rev: <스펙 파일의 최신 커밋 해시>   # git log -1 --format=%H -- <spec>. 실행 전 스펙 변경 감지용
work_plans:                          # kind: epic 일 때만. 4절 목록과 1:1 대응. single이면 이 블록을 지운다
  - id: <TASK-TICKET-1>
    title: <작업 plan 제목>
    path: <작업 plan 경로>             # 이 파일 기준 상대 경로. 예: TASK-TICKET-1/plan.md
    depends_on: []                   # 예: [TASK-TICKET-1]
    status: pending                  # pending | in_progress | done | blocked
tasks:                               # kind: single 일 때만. 4절 작업 블록과 1:1 대응. epic이면 이 블록을 지운다
  - id: T1
    title: <작업 제목>
    depends_on: []                   # 예: [T1, T2]
    status: pending                  # pending | in_progress | done | blocked
    tier: standard                   # standard(기본) | light — 작업 성격 기반 실행 등급
                                     # standard: 판단·추론이 필요한 작업 / light: 명세가 완전한 기계적 작업
                                     # 실제 모델 매핑은 실행 플랫폼이 결정 (플랫폼 중립 필드)
---

# <계획 제목>

## 1. 선택한 방식과 이유

<왜 이 접근을 선택했는지 문장으로 설명한다. 사용자가 이 계획을 승인할지
판단하는 근거가 된다. 실제로 검토한 대안만 적는다 — 검토하지 않았다면
형식을 채우기 위해 대안을 만들어내지 않는다. 감수한 트레이드오프를 함께 쓴다.
되돌리기 비싼 결정이 포함되면 여기에 표시한다 — 승인 직후 adr-writer로
ADR Proposed 작성 대상이다.>

## 2. 공통 설계

<plan-executor의 `assemble_brief.py`가 이 절(`## 2.`~`## 3.`)에서 작업 블록이 참조한 이름을 찾아
실행자 브리프의 Shared design을 만든다. 코드 블록은 헤더 주석 줄을 경계로 타입별 조각으로 나뉘므로 타입마다 헤더를 꼭 둔다 —
`// <main>/path/이름.java` 또는 `// 이름 — 설명`(이름은 그 조각이 선언하는 클래스·레코드). 메서드 시그니처만 있는
조각도 헤더가 있어야 참조 해소가 찾는다. 제목·규약을 바꾸면 스크립트 상단 상수도 함께 바꾼다.

실행자가 추측하지 않도록 구조를 여기서 정한다. 둘 이상의 작업이 공유하는 것은
여기 한 번만 적고, 작업 블록에서는 이름으로 참조한다 — 같은 시그니처를 두 곳에
적으면 한쪽만 고쳐져 어긋난다. 외부 시스템과의 API·이벤트·스키마 계약은 스펙
4절이 원본이므로 여기 반복하지 않는다. 여기는 이 애플리케이션 안의 내부 설계다.>

### 변경 파일

<실재하는 경로만. 신설 파일은 "신규", 기존 파일은 "수정". 마지막 열은 그 파일을 맡는
작업(단일이면 T번호, 에픽이면 작업 plan id). 한 파일을 두 작업이 맡으면 `depends_on`으로
순서가 정해져 있어야 한다.>

| 파일 | 신규/수정 | 변경 요지 | 작업 |
|---|---|---|---|
| `<경로>` | 수정 | <한 줄> | T1 |
| `<경로>` | 신규 | <한 줄> | T2 |

### 인터페이스

<새로 만들거나 바꾸는 함수 시그니처, DTO·레코드 필드, 메시지·로그 포맷을 대상 언어의
코드 블록으로 적는다. 산문으로 풀어 쓰지 않는다. 구현 본문은 적지 않는다 — 시그니처와
타입까지다. 기존 코드와 충돌하는 시그니처를 발견한 실행자는 바꾸지 않고 멈춰 보고한다.>

```<언어>
<시그니처 · DTO · 포맷>
```

### 결정 로직 위치

<유닛 테스트를 배정한 결정 로직(접근 판정·상태 전이·정렬/필터 규칙)을 담는 함수가
어느 파일의 무엇인지. 기본은 같은 파일의 static 메서드, IO 호출 없음. 실행자가
리액티브 체인이나 Repository 호출 사이에 끼워 넣게 두지 않는다.>

### 관련된 암묵적 동작

<작업의 결정에 관여하는 암묵적 동작 — 코드에 직접 적혀 있지 않은데 프레임워크가 대신 하는 일(애노테이션 AOP,
SpEL 캐시 키, 리플렉션 주입, 설정 기반 동작) — 을 한 줄씩. 실행자는 대상 파일만 보고 알 수 없다. **줄 끝에 근거를 붙인다** — `(확인: <파일:줄>)`,
`(확인: 실행 <명령>)`, 또는 `(추정)`. 프레임워크 동작을 확인 없이 단정하지 않는다. `(추정)`이 붙은
암묵적 동작이 관여하는 작업은 `standard`이고, 실행자는 그 줄을 믿지 않고 먼저 확인한다. 없으면 `없음`.>

## 3. 추적성

<스펙의 성공 기준 각각이 어떤 테스트로 검증되고, 그 테스트가 어느 작업에서
작성·통과되는지 매핑한다 (기준 → 테스트 → 작업). 모든 기준이 커버되어야 한다.
이 표는 기준과 테스트를 잇는 **유일한 장소**다 — 스펙 기준에도 테스트 이름에도
식별자가 없으므로, 사람과 에이전트 모두 "이 기준을 검증하는 테스트가 무엇인가",
"모든 기준이 덮였는가"를 이 표로 판정한다. 에픽이면 하위 작업 plan은 이 표를
복제하지 않고 자기 행만 인용한다. 기준 열에는 스펙의 기준 문장을 그대로 옮긴다.
테스트 이름 열의 문장이 그대로 `@DisplayName`(또는 테스트 함수 이름)이 된다:
대상 동작·조건·기대 결과가 이름만으로 드러나게 쓰고, 식별자나 번호 접두어를 붙이지
않는다. 기준 문장과 테스트 이름이 거의 같아지는 것은 정상이다. 테스트는 tdd 스킬의
5출처를 기본 도출 경로로 하며, 출처와 층(유닛/통합/E2E)을 표시한다. 5출처 밖 테스트는
출처를 `기타: <발견 근거>` 형식으로 기록한다. 테스트로 표현할 수 없는 기준은
테스트 이름을 "—"로 두고 사유를 적는다. 실행 중 테스트 이름이 바뀌면 plan-executor가
이 표를 실제 이름으로 갱신한다 — 낡은 표는 추적성 결함이다.>

| 스펙 기준 | 테스트 이름 (출처/층) | 충족 위치 |
|---|---|---|
| 만료된 토큰으로 요청하면 401을 반환한다 | "만료된 토큰으로 요청하면 401을 반환한다" (①/통합) | T1 완료 기준 |
| birthYear가 1900 미만이면 400으로 거절한다 | "birthYear가 1900 미만이면 400으로 거절한다" (②/유닛) | TASK-TICKET-2 |
| API 문서가 새 응답 형식과 일치한다 | — (문서 일치 조건, 사유: 실행 불가) | 전체 검증 항목 N |

## 4. 분할과 순서

<**에픽**: 작업 plan 목록과 그 사이 순서. 각 항목은 한 줄 — 무엇을 전달하는 수직 슬라이스인지,
어느 기준을 맡는지, 어느 작업 plan에 의존하는지. 의존 그래프가 단순 순차가 아니면 그림으로.
2~3개 작업 plan마다 체크포인트(통합 확인 지점)를 둔다. 작업 plan 하나는 브랜치·PR 하나다.
작업 plan끼리 "변경 파일"이 겹치면 `depends_on`으로 순서를 정한다. 작업 상세는 여기 적지 않는다.

**단일 티켓**: 이 절의 제목을 "4. 작업"으로 바꾸고 `work-plan-template.md`의 "작업 블록"을
T1부터 반복한다. `depends_on`이 있으면 첫 줄에 "T1 완료 후 시작"을 명시한다.>

| 작업 plan | 전달하는 동작 | 맡는 기준(묶음) | depends_on |
|---|---|---|---|
| TASK-TICKET-1 | <한 줄> | <스펙 5절 묶음 이름> | — |
| TASK-TICKET-2 | <한 줄> | <스펙 5절 묶음 이름> | TASK-TICKET-1 |

체크포인트: <TASK-TICKET-2 머지 후 — 무엇을 확인하는가>

## 5. 전체 검증

<모든 작업(또는 작업 plan) 완료 후 통합 확인 **방법**. 실행 가능한 명령, E2E 시나리오,
문서 일치 확인 절차. 무엇이 참이어야 하는지는 스펙 5절이 정하므로 반복하지 않는다 —
추적성 표에서 "전체 검증 항목 N"으로 가리킨 항목이 여기 있어야 한다.>

## 6. 위험과 롤백

<실행·배포 단계의 위험과 되돌리는 방법 — 회귀 가능 지점, 배포 순서, 데이터 되돌리기.
전제가 틀릴 위험(위험값·깨지는 조건)은 스펙 3절 소유이므로 반복하지 않는다. 없으면 `없음`.>
````

## 작성 시 체크리스트

- [ ] 복구 기록·환경 준비 기록의 제목과 빈 표가 있으며, 실행하지 않은 결과를 미리 채우지 않았는가

- [ ] `kind`에 맞는 frontmatter 블록만 남겼는가 (single → `tasks`, epic → `work_plans`)
- [ ] frontmatter `tasks`(또는 `work_plans`)와 4절이 1:1 대응하는가
- [ ] frontmatter `spec`이 승인된 스펙 문서를 가리키고 `spec_rev`가 그 파일의 현재 커밋 해시인가
- [ ] 목표·범위·성공 기준·위험값을 스펙에서 옮겨 적지 않았는가 (스펙은 링크로만)
- [ ] 추적성 표가 스펙의 모든 기준을 커버하는가 (기준 → 테스트 → 작업). 기준 열이 스펙 원문 문장과 같은가
- [ ] 추적성 표의 테스트 이름이 식별자 접두어 없이 대상 동작·조건·기대 결과를 서술하는가
- [ ] 테스트 케이스마다 출처와 층(유닛/통합/E2E)이 표시됐는가
      - 기본 출처는 ①~⑤를 사용한다.
      - 5출처 밖 테스트는 `기타: <발견 근거>` 형식으로 무엇을 왜 검증하는지 기록한다.
- [ ] 실제 인프라가 필요한 동작(롤백·캐시 무효화 등)이 통합 테스트로 배정됐는가
- [ ] 변경 파일 표의 모든 경로를 실제로 확인했고 신규/수정이 맞는가
- [ ] 인터페이스가 산문이 아니라 코드 블록이고, 외부 계약(스펙 4절)을 반복하지 않았는가
- [ ] 둘 이상 작업이 공유하는 시그니처·DTO가 2절에 한 번만 있고 작업 블록은 이름으로 참조하는가
- [ ] 작업 블록(또는 작업 plan)이 백틱으로 참조하는 이름이 2절에 같은 철자로 전부 있는가 — 없는 이름은 plan-executor가 실행을 멈춘다
- [ ] `depends_on`이 없는 작업(또는 작업 plan)끼리 변경 파일이 겹치지 않는가
- [ ] 유닛 테스트가 배정된 결정 로직은 그 위치(IO 호출 없는 함수)를 정했고, 관련된 암묵적 동작을 적었는가
- [ ] 관련된 암묵적 동작 각 줄에 근거(`확인: …` 또는 `추정`)가 있고, 추정 표기된 동작이 관여하는 작업이 `light`가 아닌가
