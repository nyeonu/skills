# 구조 배치 규칙 (task-breakdown 5단계)

수직 슬라이싱으로 작업을 나눌 때, 실행자에게 "기존 패턴에 맞춰"를 넘기지 않고 플래너가 구조를 정한다. 아래 네 규칙을 작업 내용과 대상 파일에 반영한다. 원문은 task-breakdown SKILL.md 5단계에서 이관했다.

- 작성 절차 4단계(테스트 케이스 도출)에서 유닛 층으로 배정한 **결정 로직**(접근 판정·상태 전이·정렬/필터 규칙)은 IO 호출이 없는 함수에 두고, 그 함수가 어느 파일의 무엇인지 작업 내용에 적는다.
  - 기본 형태는 **같은 파일 안의 static 메서드**다. 별도 파일로 분리하는 것은 저장소에 같은 꼴의 관례(예: 필드별 정적 검증기 클래스)가 이미 있어 그것을 따르는 경우로 한정한다. sealed 결과 타입은 결과가 셋 이상이고 Java 21 이상이며 소비처가 한 곳일 때만 지시한다 — 그때는 "소비하는 switch에 default 금지, 결정 타입은 직렬화하지 않음"을 주의사항에 적고 작업을 `standard` 등급으로 배정한다(레포에 sealed가 처음이면 "선택한 방식과 이유"에 새 패턴으로 적는다).
  - Repository·HTTP·리액티브 체인 사이에 결정을 끼우는 작업 내용은 쓰지 않는다. 테스트 대상이 아닌 두세 줄 분기는 분리하지 않는다.
- 작성 절차 2단계(컨텍스트 수집)에서 확인한 암묵적 동작이 이 작업의 결정에 관여하면 그 동작을 주의사항에 적는다. 작업이 새 애노테이션·AOP·설정 기반 동작을 도입해야 하면 계획에 명시하고, 도입 이유를 "선택한 방식과 이유"에 적는다.
- 도메인 A의 작업이 도메인 B의 `repository`·`entity`를 직접 import하게 하지 않는다. 필요하면 B의 서비스나 계약을 거치게 하고 그 경로를 작업 내용에 적는다.
- 프레임워크 제거·레이어 통합·파일 통합 같은 관례 이탈은 실행자 재량에 두지 않는다. 필요하면 "선택한 방식과 이유"에 대안과 함께 적고 ADR 후보로 표시한다. 관례에서 벗어난 구조는 실행자에게도 낯설어 실패율이 오른다.
