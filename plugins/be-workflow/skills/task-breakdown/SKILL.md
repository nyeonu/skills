# Task Breakdown

고비용 모델이 승인된 스펙을 분석·분해하고, 실행자(저비용 모델)가 그 계획대로 실행하는 워크플로우의 계획 단계 스킬이다. 산출물은 단일 `PLAN.md`이며, 사람과 에이전트가 모두 읽는다.

핵심 원칙: **계획을 읽는 실행자는 컨텍스트가 없고 추론 능력이 제한적이라고 가정하라.** "적절히 처리", "필요하면 리팩토링" 같은 판단 요구 표현은 저비용 에이전트에게 실패 지점이다. 판단은 지금 끝내고, 실행 단계에는 명확한 지시만 남겨라.

## 입력 조건

- `docs/spec/`에 `status: approved`인 스펙 문서가 있어야 한다. 없으면 중단하고 spec-writer부터 수행하도록 안내한다.
- **`scope: shared-app`(공통 스펙)은 직접 분해 대상이 아니다.** 공통 스펙에는 애플리케이션 안에서 할 일이 없다. 사용자가 공통 스펙을 지정하면, 이 저장소의 `scope: app` 스펙(`parent`가 그 공통 스펙인 것)을 찾아 그것을 분해하고, 없으면 spec-writer로 app 스펙부터 쓰도록 안내한다. 공통 스펙의 통합 성공 기준은 통합 검증 담당자의 몫이지 계획의 작업이 아니다.
- 스펙이 draft면 승인 전이므로 진행하지 않는다 — 반려된 스펙의 분해는 전부 버려지는 작업이다.

## 작성 절차

1. **스펙 로드**: 대상 스펙 문서를 읽는다. 한눈에 보기·성공 기준·제약과 경계·제외 범위가 계획의 상위 제약이 된다. frontmatter에 `parent`가 있으면 **공통 스펙도 읽고, 그 4절(계약·배포 순서)을 이 계획의 상위 제약에 더한다** — 계약 표의 엔드포인트·필드·에러 코드와 배포 순서를 작업 지시와 테스트 케이스에 그대로 쓴다. 공통 스펙이 `approved`가 아니거나 읽을 수 없으면 중단하고 사용자에게 알린다. 계약과 app 스펙이 충돌하면 코드 충돌과 마찬가지로 분해를 중단하고 스펙 수정을 요구한다. 스펙 내용을 계획에 그대로 옮겨 적지 않는다 — 실행자가 계획만 보고 작업하는 데 필요한 부분만 짧게 가져온다.
2. **컨텍스트 수집**: 대상 코드베이스를 직접 탐색하라(Glob/Grep/Read). 관련 파일의 실제 경로, 함수/클래스 이름, 기존 패턴·컨벤션을 확인한다. 추측으로 경로나 API를 쓰면 실행자가 존재하지 않는 파일을 찾다 실패한다. 작업이 건드릴 결정 로직에 관여하는 매직(애노테이션 기반 AOP, SpEL 키, 리플렉션 주입, 캐시 키에 든 권한 조건 등)이 있으면 그 동작을 확인해 두라 — 실행자는 그 파일만 보고 알 수 없으므로 해당 작업의 주의사항에 적어야 한다. **코드가 스펙과 충돌하는 사실을 발견하면 분해를 중단하고 스펙 수정을 요구한다** (spec-writer로 회귀). 충돌을 안고 쓴 계획은 실행 단계에서 반드시 터진다.
3. **의존성 그래프 파악**: 무엇이 무엇에 의존하는지 그린다 (스키마 → 모델 → API → 클라이언트 순 상향식). 구현 순서는 그래프의 바닥부터다.
4. **테스트 케이스 도출**: tdd 스킬의 5출처 절차(성공 기준 → 동등 분할·경계값 → 오류 분기 → 상태·순서 → 과거 버그)로 이 스펙의 테스트 케이스 목록을 도출한다. 5출처는 유일한 허용 목록이 아니라 누락 방지를 위한 기본 도출 경로다 — 그 밖에서 발견한 의미 있는 테스트는 출처를 `기타: <발견 근거>`로 기록한다. 각 케이스에 출처와 층(유닛/통합/E2E)을 표시한다 — 실제 인프라가 있어야 검증되는 동작(트랜잭션 롤백, 캐시 무효화 등)은 통합 테스트로 판정하고 목 기반 유닛으로 때우지 않는다. **테스트 도출은 판단 작업이므로 여기(계획 단계)서 끝낸다** — 저비용 실행자에게 "적절히 테스트 작성"을 넘기면 구현을 베낀 테스트가 나온다.
5. **수직 슬라이싱으로 분해**: 레이어별(전체 스키마 → 전체 API → 전체 UI)이 아니라 **기능 경로별**로 나눈다 — 각 작업이 완결된, 검증 가능한 동작 하나를 전달하게. 규칙:
   - 각 작업은 한 에이전트 세션에서 끝나는 크기 (파일 1~5개 수정). 5개 초과나 독립 서브시스템 2개 이상에 걸치면 더 나눈다. 작업 제목에 "그리고"가 들어가면 두 작업이다.
   - 고위험 작업(불확실성 큰 것)을 앞에 배치한다 — fail fast.
   - 작업 간 의존관계를 `depends_on`으로 명시한다. 의존 없는 작업들은 병렬 실행 후보다.
   - 2~3개 작업마다 체크포인트(통합 확인 지점)를 둔다.
   - **구현 작업의 첫 산출물은 4에서 도출한 실패하는 테스트다** (tdd의 RED) — 작업 지시에 해당 테스트 케이스를 명시하고, 완료 기준은 그 테스트의 통과로 표현한다. 검증 신뢰도가 특히 중요한 작업(핵심 로직, 과거 버그 이력이 있는 자리)은 테스트 작성과 구현을 별도 작업으로 분리한다 — 구현을 모르는 에이전트가 쓴 테스트가 구현을 베낀 테스트보다 강하다.
   - **구조 배치는 여기서 결정한다** — 실행자에게 "기존 패턴에 맞춰"를 넘기지 않는다. 작업 내용과 대상 파일에 다음을 반영한다:
     - 4에서 유닛 테스트를 배정한 **결정 로직**(접근 판정·상태 전이·정렬/필터 규칙)은 IO 호출이 없는 함수에 두고, 그 함수가 어느 파일의 무엇인지 작업 내용에 적는다. 기본 형태는 **같은 파일 안의 static 메서드**다 — 새 파일이나 sealed 결과 타입은 결과가 셋 이상이고 Java 21 이상이며 소비처가 한 곳일 때만 지시한다 — 그때는 "소비하는 switch에 default 금지, 결정 타입은 직렬화하지 않음"을 주의사항에 적고 작업을 `standard` 등급으로 배정한다(레포에 sealed가 처음이면 "선택한 방식과 이유"에 새 패턴으로 적는다). Repository·HTTP·리액티브 체인 사이에 결정을 끼우는 작업 내용은 쓰지 않는다. 테스트 대상이 아닌 두세 줄 분기는 분리하지 않는다.
     - 2에서 확인한 매직이 이 작업의 결정에 관여하면 그 동작을 주의사항에 적는다. 작업이 새 애노테이션·AOP·설정 기반 동작을 도입해야 하면 계획에 명시하고, 도입 이유를 "선택한 방식과 이유"에 적는다.
     - 도메인 A의 작업이 도메인 B의 `repository`·`entity`를 직접 import하게 하지 않는다. 필요하면 B의 서비스나 계약을 거치게 하고 그 경로를 작업 내용에 적는다.
     - 프레임워크 제거·레이어 통합·파일 통합 같은 관례 이탈은 실행자 재량에 두지 않는다. 필요하면 "선택한 방식과 이유"에 대안과 함께 적고 ADR 후보로 표시한다. 관례에서 벗어난 구조는 실행자에게도 낯설어 실패율이 오른다.
6. **실행 등급(tier) 지정**: tier는 특정 모델명이 아니라 작업의 성격을 기술한다. 실제 모델 매핑은 실행 플랫폼이 결정한다:
   - `standard`(기본): 판단·추론이 필요한 작업. 여러 파일에 걸친 로직, 기존 패턴 추론, 디버깅 가능성이 있는 작업.
   - `light`: 명세가 완전한 기계적 작업에만. 정해진 파일의 정해진 변경, 보일러플레이트, 단순 텍스트/설정 수정. 확신이 없으면 standard — 저성능 모델의 실패·재시도 비용이 단가 차이를 잠식한다.
7. **추적성 매핑 (필수)**: 스펙의 성공 기준 각 항목이 **4에서 도출한 테스트 케이스를 거쳐** 최소 하나의 작업 완료 기준 또는 전체 검증 항목에 매핑되어야 한다 (기준 → 테스트 → 작업). 매핑 표를 계획 문서에 포함한다. 이 표가 기준과 테스트를 잇는 **유일한 장소**다 — 스펙 기준에도 테스트 이름에도 식별자가 없고 둘 다 무엇을 검증하는지 서술하므로(spec-writer, tdd 스킬), 기준 열에는 스펙의 기준 문장을 그대로 옮긴다. "이 기준을 검증하는 테스트가 무엇인가", "모든 기준이 덮였는가"는 사람도 에이전트도 이 표로만 답한다. 표의 테스트 이름은 그대로 `@DisplayName`(또는 테스트 함수 이름)이 될 문장이므로 대상 동작·조건·기대 결과가 이름만으로 드러나게 쓴다. **커버리지가 안 되는 계획은 이 단계에서 반려된다** — 이것이 스펙 위반의 예방 장치다. 테스트로 표현할 수 없는 기준(문서 일치, 코드 부재 조건 등)은 테스트 없이 작업/전체 검증에 직접 매핑하고 그 사유를 적는다.
8. **PLAN.md 작성**: `references/plan-template.md`를 읽고 그 템플릿을 그대로 따라 작성한다.
9. **자체 검토**: 실행자 입장에서 다시 읽어라. "이 문서만 보고 코드베이스를 처음 보는 실행자가 작업을 끝낼 수 있는가?"에 아니오가 나오는 부분을 보강한다. 파일 경로 실재 여부, 검증 명령 실행 가능 여부를 확인한다. 서로 `depends_on`이 없는 작업들끼리 "대상 파일"이 겹치는지도 확인한다 — 겹치면 plan-executor가 병렬로 띄울 수 있으므로, 한쪽에 `depends_on`을 걸어 순서를 정하거나 한 작업으로 합친다. 같은 파일을 두 작업이 동시에 고치면 한쪽 변경이 다른 쪽에 의해 되돌려질 수 있다.
10. **승인 요청**: `status: draft`로 저장하고 사용자에게 제시한다. 선택한 방식과 이유, 범위, 추적성을 중심으로 검토를 요청한다. 실행(plan-executor)은 승인 후에만 진행된다 — 계획을 작성한 세션이 곧바로 실행까지 이어가지 않는다.
11. **ADR 후보 안내**: 계획에 되돌리기 비싼 결정(프레임워크·의존성, 데이터 모델·스키마, 인증 전략, API 아키텍처)이 포함되면 "선택한 방식과 이유"에 표시하고, **승인 직후 adr-writer로 ADR을 `Proposed`로 작성하도록** 사용자에게 안내한다 (2시점 ADR의 첫 시점).

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "스펙이 대충 이 뜻이겠지" | 해석이 필요한 스펙은 스펙 결함이다. 추측하지 말고 스펙 수정을 요구하라. |
| "경로/함수명은 대충 이럴 것이다" | 추측한 경로 하나가 실행자 하나를 통째로 실패시킨다. Glob/Grep으로 확인하는 데 몇 초면 된다. |
| "작업이 많으니 뒤쪽은 간단히 써도 되겠지" | 실행자는 앞뒤 작업을 구분하지 않는다. 마지막 작업도 첫 작업과 같은 상세도로 쓴다. |
| "verify는 실행할 때 알아서 정하면 된다" | verify 없는 작업은 실행자가 성공을 판단할 수 없어 재작업 루프를 만든다. 지금 정하라. |
| "추적성 매핑은 형식적이니 생략하자" | 매핑에서 빠진 기준 하나가 곧 스펙 위반 하나다. 테스트 이름에 기준 식별자가 없으므로 이 표가 없으면 어느 테스트가 어느 기준을 검증하는지 아무도 답할 수 없다. 5번 검증(spec-conformance-check)에서 터지는 것보다 지금 잡는 게 싸다. |
| "테스트는 실행자가 알아서 만들면 된다" | 테스트 도출은 판단 작업이고, 구현자가 만든 테스트는 구현의 거울이 된다. 어떤 테스트를 만들지는 계획의 산출물이다 (tdd 스킬 5출처). |
| "코드 구조는 실행자가 기존 패턴 보고 맞추면 된다" | 결정 로직을 어디에 둘지는 판단 작업이다. 실행자는 파일 몇 개만 보고 일하므로 눈앞의 서비스 메서드 안에 판정을 끼워 넣는다 — 그 결과가 판정과 무관한 Repository·HTTP 목을 세워야만 테스트되는 코드다. 위치는 계획이 정한다. |
| "레이어별로 나누는 게 깔끔하다" | 수평 슬라이스는 마지막 통합까지 아무것도 검증 못 한다. 수직 슬라이스는 작업마다 동작을 전달한다. |
| "문서가 길어지니 선택 이유는 생략하자" | 선택한 방식과 이유가 없으면 사용자가 승인할 근거가 없고, 실행 중 수정 시 원래 의도를 잃는다. |
| "대안 항목이 비니 형식상 몇 개 만들자" | 검토하지 않은 대안을 적는 것은 승인 근거를 위조하는 것이다. 실제로 검토한 대안만 적고, 없으면 없다고 쓴다. |

## 좋은 작업 지시 vs 나쁜 작업 지시

**나쁨**: "인증 로직을 개선한다."
**좋음**: "`src/auth/session.ts`의 `validateSession()`에 토큰 만료 검사를 추가한다. 만료 시 `TokenExpiredError`(이미 `src/errors.ts`에 정의됨)를 던진다. 기존 호출부 3곳(`api/middleware.ts:42`, ...)은 수정하지 않는다."

차이: 좋은 지시는 파일 경로, 사용할 기존 코드, 건드리지 말 범위를 모두 담아 실행자의 추측을 제거한다.

## 산출물 위치와 파일명

- 저장: `{프로젝트 루트}/docs/plan/YYYY-MM-DD-<브랜치명>-<계획-주제-kebab-case>.md`. 디렉터리가 없으면 생성한다. 브랜치명은 `git branch --show-current`로 확인하고, `/`가 포함되면 `-`로 치환한다 (예: `feature/login` → `feature-login`).
- frontmatter의 `spec` 필드에 원본 스펙 문서 경로를, `spec_rev`에 그 파일의 최신 커밋 해시(`git log -1 --format=%H -- <스펙 경로>`)를 기록한다. `parent`가 있으면 `parent_spec`과 `parent_spec_rev`도 같은 방식으로 기록한다(다른 저장소면 그 저장소에서 실행). plan-executor가 실행 전에 이 값으로 "계획 이후 스펙이 바뀌었는지"를 기계적으로 확인한다.
- 사용자가 다른 경로를 지정하면 그것을 따른다.
