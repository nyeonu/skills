# Spec Conformance Check

plan-executor의 검증은 "계획대로 됐는가"까지다. 계획이 스펙을 잘못 번역했다면 — 성공 기준 하나가 계획에서 누락·왜곡됐다면 — 작업별 verify와 전체 검증이 전부 통과해도 스펙 위반은 남는다. 이 스킬은 그 간극을 잡는다: **"맞는 것을 만들었는가"**를 스펙만 기준으로 독립 검증한다.

## 워크플로우 상 위치

plan-executor 완료 후, 품질 검토(review 3종) 전에 수행한다. **fail-fast 게이트**: 여기서 실패하면 품질 검토를 수행하지 않고 task-breakdown(계획 수정)으로 회귀한다 — 기능이 틀린 코드의 품질 리뷰는 버려지는 작업이다.

## 격리 원칙 (핵심)

검증자는 fresh-context 서브에이전트로 스폰하고, **스펙 문서와 구현물(코드베이스)만 제공한다.**

- **계획 문서(docs/plan/)를 주지 않는다.** 계획이 스펙을 잘못 번역했다면 검증자가 그 오류를 그대로 물려받는다. 검증자는 스펙 → 구현을 직접 대조해야 한다.
- 실행 세션의 대화 맥락도 주지 않는다. "구현하면서 이렇게 해석했다"는 정보는 검증 오염원이다.
- 오케스트레이터 자신이 실행을 지휘했던 세션이라면, 자신의 판단을 재검증하는 이해충돌이 있으므로 반드시 서브에이전트로 격리한다.

## 검증 절차

1. **스펙 로드**: `docs/spec/`에서 대상 스펙을 읽는다. 성공 기준(SC-N) 목록이 검증 단위다. frontmatter에 `parent`가 있으면 공통 스펙도 읽어 **4절의 계약(엔드포인트·필드·에러 코드)과 배포 순서 제약을 검증 항목에 추가한다** — 계약 방식이 코드 우선이고 스냅샷 파일이 있으면 계약 표와 스냅샷 파일을 대조한다. 공통 스펙 5절의 통합 SC는 애플리케이션 둘 이상이 배포된 뒤에야 확인되므로 **이 검증의 범위 밖**이다. 보고서에 범위 밖임과 검증 담당자를 명시한다. `scope: shared-app` 스펙 자체를 대상으로 지정받으면, 통합 검증 환경(스테이징 등)이 준비됐는지 사용자에게 확인하고 그 환경에서 통합 SC만 검증한다.
2. **검증자 스폰**: fresh-context 서브에이전트에게 스펙 전문과 레포 접근만 제공한다.
3. **성공 기준 순회 검증**: SC-N 각각에 대해 검증자는:
   - 해당 기준을 충족해야 할 실제 동작을 특정한다
   - **실행 가능한 방법으로 확인한다**: 테스트 실행, 빌드, API 호출(curl), 실제 시나리오 재현. 코드를 읽고 "구현되어 있는 것 같다"는 판정이 아니다 — 증거 없는 통과는 통과가 아니다.
   - 기존 테스트를 증거로 쓸 때는 그 테스트가 해당 SC를 실제로 검증하는지 내용을 확인한다 — 이름만 맞는 테스트, skip된 테스트는 증거가 아니다.
   - UI가 포함되면 브라우저 기반 검증(browser-testing-with-devtools 등 가용 도구)을 사용한다
4. **SC 태그 추적성 확인**: 테스트 코드에 SC 태깅(`@DisplayName("SC-N: …")` 등)이 있으면, 태그의 SC 번호가 **현행 스펙**의 번호와 일치하는지 확인한다. 스펙이 통합·재번호됐는데 태그가 옛 번호를 가리키면 추적성 끊김으로 보고한다 — 번호가 어긋난 매핑은 다음 검증부터 장식이 된다.
5. **경계·제외 범위 확인**: 스펙의 "하지 않을 것"이 지켜졌는지, 제외 범위 밖의 변경(시키지 않은 개선)이 없는지 확인한다.
6. **보고**: 기준별 판정을 취합한다.

## 보고 포맷

보고서는 한국어 산출물이다. 목차와 `PASS`/`FAIL` 값은 고정이고, 문장과 분량은 검증 규모에 맞게 조절한다. 필수 항목에 쓸 내용이 없으면 일반론으로 채우지 말고 `없음`이라고 쓴다. 코드만 읽고 내린 통과 판정은 금지다 — 모든 PASS에는 실행 증거가 있어야 한다.

```markdown
# 스펙 적합성 검증

- 대상 스펙: docs/spec/<파일명>
- 공통 스펙: <parent 위치, 없으면 "없음">
- 판정: PASS | FAIL

## 기준별 결과

| 성공 기준 | 판정 | 실행 증거 |
|---|---|---|
| SC-1: <요약> | PASS | <실행한 명령과 결과 요약> |
| SC-2: <요약> | FAIL | <기대 동작 vs 실제 동작, 재현 방법> |

## 계약 준수

<parent가 있을 때만. 공통 스펙 4절의 계약 항목별 준수 여부와 증거. 코드 우선이면 계약 표 ↔ 스냅샷 파일 대조 결과. 없으면 "해당 없음">

## 범위 밖 (통합 SC)

<공통 스펙 5절의 통합 SC 목록과 각 검증 담당자. 이 보고서는 판정하지 않는다. parent가 없으면 "해당 없음">

## 경계 위반

<스펙의 "하지 않을 것" 위반, 범위 밖 변경. 없으면 "없음">

## 실패 상세

<각 실패의 재현 절차, 추정 원인(가능하면 — 사실과 추정을 구분해 쓴다), 관련 파일. FAIL이 없으면 "없음">

## 남은 불확실성

<실행으로 확인하지 못한 부분과 그 이유. 없으면 "없음">
```

## 판정 후 처리

- **전체 PASS**: 스펙 frontmatter의 `status`를 `approved`에서 `implemented`로 바꾼다 — 완료된 스펙이 `approved`로 남으면 다음 세션의 라우팅이 이미 끝난 스펙을 다시 분해하려 든다. 이 상태 변경은 검증자가 아니라 오케스트레이터가 한다(검증자는 레포를 수정하지 않는다). 이후 품질 검토(review 3종) 진행 가능. 계획에 연결된 `Proposed` ADR이 있으면 adr-writer로 `Accepted` 확정을 진행한다.
- **하나라도 FAIL**: 품질 검토로 진행하지 않는다. 보고서를 근거로 task-breakdown에서 수정 계획을 작성한다(승인 게이트 포함). 오케스트레이터나 검증자가 직접 수정하지 않는다 — 검증자가 수정까지 하면 격리가 깨진다.

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "전체 검증이 통과했으니 스펙도 맞을 것이다" | 전체 검증은 계획 기준이다. 계획의 번역 오류는 계획 기준 검증으로 잡을 수 없다. |
| "계획 문서를 주면 검증이 빨라진다" | 빨라지는 게 아니라 오염된다. 계획의 해석을 물려받은 검증은 독립 검증이 아니다. |
| "코드를 읽어보니 구현되어 있다" | 읽어서 아는 것은 존재이지 동작이 아니다. 실행 증거를 남겨라. |
| "사소한 FAIL이니 품질 검토를 병행하자" | 수정이 생기면 검토 대상 코드가 바뀐다. FAIL이 있으면 검토는 전부 재작업이 된다. |
| "검증자가 발견한 김에 바로 고치게 하자" | 검증과 수정을 한 에이전트가 하면 격리가 깨지고, 수정이 승인 게이트를 우회한다. |

## 검증

- [ ] 검증자가 fresh-context 서브에이전트로 격리됐는가
- [ ] 검증자에게 계획 문서·실행 맥락을 주지 않았는가
- [ ] 모든 SC-N에 실행 증거가 있는 판정이 붙었는가
- [ ] SC 태깅된 테스트가 있으면 태그 번호가 현행 스펙과 일치하는가
- [ ] 경계·제외 범위 위반을 확인했는가
- [ ] parent가 있으면 공통 스펙 4절의 계약을 검증했고, 통합 SC는 범위 밖으로 명시했는가
- [ ] FAIL 시 수정 없이 task-breakdown 회귀로 보고됐는가
- [ ] 전체 PASS 시 스펙 `status`를 `implemented`로 갱신했는가
