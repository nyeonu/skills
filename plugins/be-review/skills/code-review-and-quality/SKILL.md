# 코드 리뷰와 품질

머지 전 변경을 정확성·가독성·아키텍처·테스트 품질 중심으로 검토하고, 보안·성능은 명백한 위험만 1차로 포착해 전문 스킬로 연결하는 리뷰 스킬이다.

**승인 기준:** 변경이 완벽하지 않더라도 전체 코드 건강도(code health)를 확실히 개선하고 프로젝트 컨벤션을 따르면 승인한다. 자신이 작성했을 방식과 다르다는 이유로 막지 마라 — 목표는 완벽함이 아니라 지속적 개선이다.

## 사용 시점

- PR이나 변경 사항을 머지하기 전
- 다른 에이전트나 모델이 생성한 코드를 평가할 때
- 버그 수정 후 (수정과 회귀 테스트를 함께 리뷰)

보안이 주제인 변경(인증·입력 처리·시크릿)은 `security-and-hardening`, 성능 분석·최적화는 `performance-optimization`이 전담한다. 이 스킬의 보안·성능 확인은 명백한 위험을 놓치지 않기 위한 얕은 1차 점검이다.

## 리뷰 절차

### 1. 맥락 확인과 참고자료 로드 판정

코드를 보기 전에 의도를 파악한다: 이 변경이 이루려는 것, 구현 대상 스펙 또는 작업, 기대되는 동작 변화. 스펙이 있으면 그 성공 기준이 정확성 판단의 기준이 된다.

이어서 diff와 작업 목적을 보고 **참고자료 로드 여부를 판정한다.** 해당 조건이면 4단계(발견 사항 분류) 전에 반드시 읽는다 — 권고가 아니라 계약이다:

- 인증·인가·세션·토큰·쿠키·외부 입력·파일 업로드·시크릿·PII·외부 연동·의존성 변경이 있으면 → `references/security-checklist.md`
- DB 조회·목록 API·외부 호출·캐시·락·풀·동시성·CPU·메모리·대용량 처리 변경이 있으면 → `references/performance-checklist-backend.md`, UI 렌더링 변경이 있으면 → `references/performance-checklist-frontend.md`
- 두 조건에 모두 해당하면 해당하는 참고자료를 모두 읽는다
- 해당 여부가 불분명하면 누락 방지를 위해 읽는 쪽을 선택한다

### 2. 테스트 먼저 리뷰

테스트는 의도와 커버리지를 드러낸다. 확인할 것: 변경에 대한 테스트가 존재하는가, 구현 세부가 아니라 동작을 검증하는가, **이름이 무엇을 검증하는지 서술하는가** (대상 동작·조건·기대 결과가 이름만으로 드러나는가 — `test1`·`저장 테스트`처럼 모호한 이름과 `SC-13: …`·`기준 2 검증`처럼 식별자·번호에 기대는 이름은 결함이다. 기준과 테스트의 연결은 계획의 추적성 표가 담당한다), 코드가 잘못 바뀌면 회귀를 잡아내는가.

"엣지 케이스를 커버하는가"는 감으로 판정하지 말고 **테스트 도출 5출처**를 렌즈로 훑어라 — 각 출처에서 빠진 묶음이 곧 커버리지 구멍이다:

| 출처 | 리뷰 질문 |
|---|---|
| ① 성공 기준 | 이 변경이 구현하는 스펙 기준 각각에 대응 테스트가 있는가 — 계획의 추적성 표가 있으면 그 표를 기준선으로 대조하고, 표에 없는 기준이나 실제 테스트와 어긋난 행은 추적성 결함으로 적는다 |
| ② 동등 분할·경계값 | 입력 묶음(정상/없음/형식 오류/누락)과 경계(0건·1건·최대·최대+1)에서 빠진 대표가 있는가 |
| ③ 오류 분기 | diff에서 **사용자 관찰 동작이 달라지는 의사결정 분기와 실패 경로**(의존성 실패, 권한 없음 등)에 대응 테스트가 있는가 — 리뷰 시점엔 실제 코드가 있으므로 계획 단계 도출이 놓친 분기를 여기서 잡는다 |
| ④ 상태·순서 | 멱등성, 수정 직후 조회, 트랜잭션 실패 복원이 관련 있다면 검증되는가 |
| ⑤ 과거 버그 | 버그 수정이라면 수정 전에 실패했을 재현 테스트가 포함됐는가 |

주의: 실제 인프라가 있어야 검증되는 동작(트랜잭션 롤백, 캐시 무효화의 실제 적중)을 목(mock) 기반 유닛 테스트가 "호출 확인"으로 때우고 있으면 커버된 것이 아니다 — 통합 테스트를 요구하라.

### 3. 구현 리뷰

변경된 파일마다 네 축으로 본다:

- **정확성**: 스펙·요구사항과 일치하는가. 엣지 케이스(null, 빈 값, 경계값)와 오류 경로가 처리되는가. 오프바이원(off-by-one), 레이스 컨디션, 상태 불일치가 있는가.
- **가독성·단순성**: 작성자의 설명 없이 이해되는가. 이름이 서술적이고 컨벤션과 일치하는가. 더 적은 줄로 가능한가. 추상화가 복잡성에 걸맞은 가치를 내는가(세 번째 사용 사례 전에 일반화하지 마라). 죽은 코드 잔재(no-op 변수, 하위 호환 심(shim), `// removed` 주석)가 없는가.
- **아키텍처**: 기존 패턴을 따르는가, 새 패턴이면 정당한 이유가 있는가. 모듈 경계와 의존성 방향이 유지되는가(순환 의존성 없음). 공유해야 할 중복이 없는가.
- **보안·성능 1차 확인** (명백한 위험만): 파라미터화되지 않은 쿼리, 코드·로그의 시크릿, 인증·인가 검사 누락, 검증 없는 외부 입력 / N+1 쿼리, 무제한(unbounded) 조회, 페이지네이션 없는 목록 엔드포인트. 1단계에서 로드한 참고자료의 해당 항목을 기준으로 점검한다. 전문 검토가 필요한 문제를 발견하면 "전문 스킬 검토 필요"로 끝내지 말고, **이 리뷰에서 무엇까지 확인했고 무엇을 확인하지 못했는지(확인 한계)와 후속 검토 대상(`security-and-hardening` / `performance-optimization` 중 무엇을, 어떤 문제에 대해)**을 발견 사항에 명시한다.

새 의존성이 추가됐다면: 기존 스택으로 해결되는지, 유지보수되고 있는지, 알려진 취약점이 없는지(저장소 생태계에 맞는 감사 도구 기준), 라이선스가 호환되는지 확인한다. 모든 의존성은 부채다.

### 4. 심각도 분류

모든 발견 사항은 다음 세 등급 중 하나다. 다른 라벨(Nit, FYI 등)을 만들지 않는다:

| 등급 | 의미 |
|---|---|
| `Critical` | 보안 취약점, 데이터 손실, 명백한 기능 파손 등 머지 차단 |
| `Important` | 머지 전에 해결해야 할 정확성·설계·테스트 문제 |
| `Suggestion` | 선택적 개선 제안 — 작성자가 무시해도 됨 |

모든 `Critical`과 `Important`에는 **파일과 줄, 확인한 사실, 실제 영향, 구체적인 수정 방향**을 포함한다. "느릴 수 있다"가 아니라 측정하거나 추정임을 밝힌다.

### 5. 실행 증거 확인

diff 전체를 읽었는지, 그리고 작성자의 검증 스토리를 확인한다: 어떤 테스트를 실행했는가, 빌드가 통과했는가, 수동 확인이 필요한 변경이면 그 증거가 있는가. 실행 증거 없는 "테스트 통과" 주장은 확인값이 아니라 추정값으로 취급한다.

## 판정과 출력

판정은 두 값뿐이다: `Critical` 또는 `Important`가 하나라도 있으면 `REQUEST CHANGES`, 없으면 `APPROVE`.

출력은 발견 사항부터(findings-first) 쓴다. 이 형식은 `code-reviewer` 에이전트와 동일한 계약이다:

```markdown
## 리뷰 요약

**판정:** APPROVE | REQUEST CHANGES

**개요:** [변경 내용과 전체 평가 1~2문장. 결론부터 쓴다]

### Critical
- [파일:줄] [사실 → 영향 → 수정 권고]

### Important
- [파일:줄] [사실 → 영향 → 수정 권고]

### Suggestion
- [파일:줄] [제안 내용]

### 잘된 점
- [실제로 확인한 긍정 관찰만. 확인한 것이 없으면 이 섹션을 생략한다]

### 검증 확인
- 테스트 리뷰: [했음/안 했음, 관찰 내용]
- 빌드 확인: [했음/안 했음]
- 보안·성능 1차 확인: [했음/안 했음, 관찰 내용]
- 읽은 참고자료: [파일명 또는 해당 없음]
- 전문 검토 연결: [필요 여부와 이유]
```

이슈가 없을 때는 억지로 칭찬을 만들지 말고, **잔여 위험과 검증 공백**(리뷰로 확인하지 못한 것, 실행하지 못한 검증)을 보고한다.

## 리뷰 원칙

- **고무도장 금지.** 근거 없는 "LGTM"은 리뷰가 아니다. 실제 문제를 완곡하게 표현하지 마라 — 프로덕션에서 터질 버그를 "사소한 우려"라 부르는 것은 부정직하다.
- **기술적 사실과 데이터가 의견을 이긴다.** 스타일 문제는 스타일 가이드가 권위다. 작성자가 전체 맥락을 알고 다르게 판단하면 수용하고, 코멘트는 사람이 아니라 코드에 대해 한다.
- **"나중에 정리하겠다"를 수용하지 마라.** 미뤄진 정리는 거의 이루어지지 않는다. 이번 변경에서 처리할 수 없으면 추적되는 이슈 등록을 요구하라.
- **리뷰하기에 너무 큰 변경은 분할을 요청하라.** 리팩터링과 기능 추가가 섞인 변경은 두 개의 변경이다. 예외는 파일 삭제·자동화된 리팩터링처럼 의도만 확인하면 되는 경우다.
- **죽은 코드는 목록화하고 물어라.** 도달 불가능해진 코드를 발견하면 명시적으로 나열하고 제거 여부를 확인받는다. 말없이 삭제하지 않는다.
- **AI가 생성한 코드는 더 많은 검증이 필요하다.** 틀렸을 때조차 자신만만하고 그럴듯하다. 테스트 통과는 필요조건이지 충분조건이 아니다.

## 검증

리뷰 완료 전 확인:

- [ ] 참고자료 로드 조건을 판정하고, 해당하는 참고자료를 발견 사항 분류 전에 읽었는가
- [ ] 테스트를 먼저 리뷰하고 5출처 렌즈로 커버리지 구멍을 확인했는가
- [ ] 모든 발견 사항이 `Critical`/`Important`/`Suggestion` 중 하나로 분류됐는가
- [ ] `Critical`/`Important`마다 파일·줄, 사실, 영향, 수정 방향이 있는가
- [ ] 판정이 규칙대로인가 (`Critical`/`Important` 존재 → `REQUEST CHANGES`)
- [ ] 이슈가 없으면 잔여 위험과 검증 공백을 보고했는가
- [ ] 전문 검토가 필요한 발견에 확인 한계와 후속 검토 대상을 명시했는가
