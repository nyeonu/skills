# 보안과 하드닝

모든 외부 입력은 적대적인 것으로, 모든 시크릿(secret)은 유출되면 안 되는 것으로, 모든 인가(authorization) 검사는 필수로 취급한다. 보안은 별도 단계가 아니라 사용자 데이터·인증·외부 시스템을 다루는 모든 코드에 걸리는 제약이다.

**필수 참고자료 로드**: 이 스킬이 발동하면 `references/security-checklist.md`를 **항상 읽은 후** 구현 또는 검토를 시작한다. 이 스킬에서 참고자료는 선택 사항이 아니다 — 점검 항목, 코드 예시, 추적 중인 공식 출처의 버전 기록이 그 파일에 있다.

## 사용 시점

- 사용자 입력을 받는 기능, 파일 업로드, 웹훅(webhook), 콜백을 만들 때
- 인증 또는 인가를 구현하거나 변경할 때
- 민감한 데이터(PII, 결제 정보)를 저장·전송할 때
- 외부 API나 서비스와 연동할 때

## 3단계 경계 시스템

### 항상 할 것 (예외 없음)

- 모든 외부 입력을 **시스템 경계에서**(API 라우트, 폼 핸들러) 검증한다 — 허용 목록(allowlist) 기준
- 모든 데이터베이스 쿼리를 파라미터화한다 — 사용자 입력을 SQL에 문자열로 이어붙이지 않는다
- 출력을 인코딩해 XSS를 방지한다 — 프레임워크의 자동 이스케이프를 쓰고 우회하지 않는다
- 모든 외부 통신에 HTTPS를 쓴다
- 비밀번호는 아래 "비밀번호 저장" 기준으로 해시한다 — 평문·단순 해시(MD5, SHA 계열 단독) 금지
- 보안 헤더를 설정한다 (CSP, HSTS, X-Frame-Options, X-Content-Type-Options)
- 세션 쿠키는 httpOnly, secure, sameSite로 설정한다
- 릴리스 전에 저장소 생태계에 맞는 의존성 감사를 실행한다 (아래 "의존성 위험")

### 먼저 물어볼 것 (사람의 승인 필요)

- 새 인증 플로우 추가 또는 인증 로직 변경
- 새로운 범주의 민감 데이터(PII, 결제 정보) 저장
- 새 외부 서비스 연동, 파일 업로드 핸들러 추가
- CORS 설정 변경, 레이트 리미팅(rate limiting) 수정
- 상승된 권한이나 역할(role) 부여

### 절대 하지 말 것

- 시크릿을 버전 관리에 커밋 (API 키, 비밀번호, 토큰)
- 민감한 데이터 로깅 (비밀번호, 토큰, 전체 카드 번호)
- 클라이언트 측 검증을 보안 경계로 신뢰
- 편의를 위한 보안 헤더·보안 제어 비활성화 — **보안 제어를 끄는 것은 어떤 경우에도 "수정"이 아니다**
- 사용자 제공 데이터와 함께 `eval()`·`innerHTML` 사용
- 인증 토큰을 클라이언트에서 접근 가능한 저장소(localStorage)에 저장
- 스택 트레이스나 내부 오류 세부 정보를 사용자에게 노출

## 비밀번호 저장

기준 출처는 OWASP Password Storage Cheat Sheet다. 확인일과 출처 버전(commit SHA)은 `references/security-checklist.md`의 출처 메타데이터에 기록되어 있다 — 평소에는 그 기록값을 쓰고 매 작업마다 원문을 조회하지 않는다.

**공식 출처 재확인 조건** — 다음의 경우에는 기록값 대신 공식 문서를 다시 확인한다:

- 신규 비밀번호 저장 방식을 설계할 때
- 해시 알고리즘이나 파라미터를 변경·마이그레이션할 때
- Argon2id·scrypt·bcrypt·PBKDF2의 구체적 설정값을 운영 기본값으로 확정할 때
- 참고자료의 `상태`가 `needs_review`일 때
- 참고자료의 `확인일`이 작업일 기준 30일을 넘었을 때 — 이 스킬을 실행하는 주체가 참고자료의 신선도 확인 규칙을 수행한다

그 밖의 단순 코드 리뷰나 기존 기준을 그대로 적용하는 작업에서는 기록된 기준을 사용한다.

- **신규 시스템은 Argon2id 우선.** OWASP 최소 설정: 메모리 19MiB, 반복 2회, 병렬화 1 (동등 보안의 다른 조합 가능).
- Argon2id를 쓸 수 없으면 **scrypt**를 검토한다.
- **bcrypt는 레거시 호환 대안이다** — 신규 시스템의 기본값이 아니다. 쓸 때는 OWASP 공식 최소 work factor(10 이상)와 서버 응답 시간 측정을 함께 고려해 값을 정하고, 72바이트 입력 제한을 인지한다. "rounds ≥ 12" 같은 고정 규칙을 모든 시스템에 강제하지 않는다 — 하드웨어에 따라 적정값이 다르다.
- FIPS-140 준수가 요구되면 PBKDF2를 쓴다.
- 레거시 해시(MD5, SHA-1)는 마이그레이션 계획을 세운다 — 기존 해시를 새 알고리즘의 입력으로 감싸거나, 로그인 시 재해시.

## 핵심 점검 영역

- **신뢰 경계**: 외부에서 오는 모든 데이터(API 응답, 로그, 사용자 콘텐츠, 설정 파일)는 신뢰할 수 없는 것으로 취급하고, 로직·렌더링에 쓰이기 전에 경계에서 검증한다.
- **인증·인가**: 인증(누구인가)과 인가(무엇을 할 수 있는가)를 구분한다. 보호된 모든 엔드포인트에서 인가를 확인하고, 리소스 접근 시 소유권·역할을 확인한다(IDOR 방지). 재설정 토큰은 시간 제한·1회용.
- **시크릿과 민감 정보**: 시크릿은 환경 변수·시크릿 매니저에 두고 코드·로그·응답에서 제외한다. `.gitignore`에 시크릿 파일 패턴을 포함하고, 커밋 전 스테이징된 diff에서 시크릿 패턴을 확인한다.
- **외부 연동**: 웹훅 페이로드는 서명을 검증한다. OAuth는 PKCE와 state 파라미터를 쓴다. 아웃바운드 요청 대상 URL은 허용 목록으로 제한한다(SSRF 방지).
- **의존성 위험**: 아래 참조.

## 의존성 위험

저장소의 패키지 생태계에 맞는 감사 도구를 쓴다. `npm audit`은 Node 프로젝트의 예시일 뿐이다 — Gradle/Maven은 OWASP Dependency-Check나 조직이 쓰는 SCA 도구, Python은 `pip-audit` 등 저장소와 CI가 이미 쓰는 표준 도구를 먼저 확인한다.

결과는 심각도만으로 판단하지 않는다:

- 취약한 코드가 실제 코드 경로에서 도달 가능한가?
- 런타임 의존성인가, 개발 전용(dev-only)인가?
- 배포 컨텍스트에서 실제로 악용 가능한가?

도달 가능한 critical/high는 즉시 수정(업데이트·패치·교체), 수정을 미룰 때는 사유와 재검토 날짜를 문서화한다.

## 보고 방식

- **확인값과 추정값을 구분한다.** 실행·재현으로 확인한 취약점과 코드만 읽고 추정한 위험을 표시를 다르게 해 보고한다.
- 발견 사항마다 사실(무엇이 문제인가), 영향(공격자가 무엇을 할 수 있는가), 구체적 수정 권고를 쓴다.
- 고정 수치(레이트 리미팅 창·횟수, 세션 만료, 토큰 수명)는 공식 표준이 아니라 예시 또는 프로젝트 기본값임을 명시한다. 프로젝트에 정해진 값이 있으면 그 값이 기준이다.

## 검증

보안 관련 코드를 구현·검토한 후:

- [ ] `references/security-checklist.md`를 읽은 후 작업을 시작했는가
- [ ] 의존성 감사(생태계 표준 도구)에서 도달 가능한 critical/high 취약점 없음
- [ ] 소스 코드나 git 히스토리에 시크릿 없음
- [ ] 모든 사용자 입력이 시스템 경계에서 검증됨
- [ ] 보호된 모든 엔드포인트에서 인증과 인가를 확인
- [ ] 오류 응답이 내부 세부 정보를 노출하지 않음
- [ ] 확인값과 추정값을 구분해 보고했음
