# Task Breakdown

고비용(고성능) 에이전트가 승인된 스펙을 분석·분해하고, 저비용 에이전트가 그 계획대로 실행하는 워크플로우의 계획 단계 스킬이다. 산출물은 단일 `PLAN.md`이며, 사람과 에이전트가 모두 읽는다.

기존 plan-writer에서 요구사항 인터뷰를 분리(→ interview-me, spec-writer)하고 addyosmani `planning-and-task-breakdown`의 분해 방법론과 추적성 규칙을 더한 버전이다.

핵심 원칙: **계획을 읽는 실행자는 컨텍스트가 없고 추론 능력이 제한적이라고 가정하라.** "적절히 처리", "필요하면 리팩토링" 같은 판단 요구 표현은 저비용 에이전트에게 실패 지점이다. 판단은 지금 끝내고, 실행 단계에는 명확한 지시만 남겨라.

## 입력 조건

- `docs/spec/`에 `status: approved`인 스펙 문서가 있어야 한다. 없으면 중단하고 spec-writer부터 수행하도록 안내한다.
- 스펙이 draft면 승인 전이므로 진행하지 않는다 — 반려된 스펙의 분해는 전부 버려지는 작업이다.

## 작성 절차

1. **스펙 로드**: 대상 스펙 문서를 읽는다. 목표·성공 기준(SC-N)·경계·제외 범위가 계획의 상위 제약이 된다.
2. **컨텍스트 수집**: 대상 코드베이스를 직접 탐색하라(Glob/Grep/Read). 관련 파일의 실제 경로, 함수/클래스 이름, 기존 패턴·컨벤션을 확인한다. 추측으로 경로나 API를 쓰면 실행 에이전트가 존재하지 않는 파일을 찾다 실패한다. **코드가 스펙과 충돌하는 사실을 발견하면 분해를 중단하고 스펙 수정을 요구한다** (spec-writer로 회귀). 충돌을 안고 쓴 계획은 실행 단계에서 반드시 터진다.
3. **의존성 그래프 파악**: 무엇이 무엇에 의존하는지 그린다 (스키마 → 모델 → API → 클라이언트 순 상향식). 구현 순서는 그래프의 바닥부터다.
4. **수직 슬라이싱으로 분해**: 레이어별(전체 스키마 → 전체 API → 전체 UI)이 아니라 **기능 경로별**로 나눈다 — 각 작업이 완결된, 검증 가능한 동작 하나를 전달하게. 규칙:
   - 각 작업은 한 에이전트 세션에서 끝나는 크기 (파일 1~5개 수정). 5개 초과나 독립 서브시스템 2개 이상에 걸치면 더 나눈다. 작업 제목에 "그리고"가 들어가면 두 작업이다.
   - 고위험 작업(불확실성 큰 것)을 앞에 배치한다 — fail fast.
   - 작업 간 의존관계를 `depends_on`으로 명시한다. 의존 없는 작업들은 병렬 실행 후보다.
   - 2~3개 작업마다 체크포인트(통합 확인 지점)를 둔다.
5. **실행 등급(tier) 지정**: tier는 특정 모델명이 아니라 작업의 성격을 기술한다. 실제 모델 매핑은 실행 플랫폼이 결정한다:
   - `standard`(기본): 판단·추론이 필요한 작업. 여러 파일에 걸친 로직, 기존 패턴 추론, 디버깅 가능성이 있는 작업.
   - `light`: 명세가 완전한 기계적 작업에만. 정해진 파일의 정해진 변경, 보일러플레이트, 단순 텍스트/설정 수정. 확신이 없으면 standard — 저성능 모델의 실패·재시도 비용이 단가 차이를 잠식한다.
6. **추적성 매핑 (필수)**: 스펙의 성공 기준 각 항목(SC-N)이 최소 하나의 작업 완료 기준(acceptance) 또는 전체 검증(Final Verification) 항목에 매핑되어야 한다. 매핑표를 계획 문서에 포함한다. **커버리지가 안 되는 계획은 이 단계에서 반려된다** — 이것이 스펙 위반의 예방 장치다.
7. **PLAN.md 작성**: `references/plan-template.md`를 읽고 그 템플릿을 그대로 따라 작성한다.
8. **자체 검토**: 실행 에이전트 입장에서 다시 읽어라. "이 문서만 보고 코드베이스를 처음 보는 에이전트가 작업을 끝낼 수 있는가?"에 아니오가 나오는 부분을 보강한다. 파일 경로 실재 여부, 검증 명령 실행 가능 여부를 확인한다.
9. **승인 요청**: `status: draft`로 저장하고 사용자에게 제시한다. 판단 근거와 범위, 추적성 매핑을 중심으로 검토를 요청한다. 실행(plan-executor)은 승인 후에만 진행된다 — 계획을 작성한 세션이 곧바로 실행까지 이어가지 않는다.
10. **ADR 후보 안내**: 계획에 되돌리기 비싼 결정(프레임워크·의존성, 데이터 모델·스키마, 인증 전략, API 아키텍처)이 포함되면 판단 근거에 표시하고, **승인 직후 adr-writer로 ADR을 `Proposed`로 작성하도록** 사용자에게 안내한다 (2시점 ADR의 첫 시점).

## 타협 금지 (Anti-Rationalization)

| 떠오르는 변명 | 실제 |
|---|---|
| "스펙이 대충 이 뜻이겠지" | 해석이 필요한 스펙은 스펙 결함이다. 추측하지 말고 스펙 수정을 요구하라. |
| "경로/함수명은 대충 이럴 것이다" | 추측한 경로 하나가 실행 에이전트 하나를 통째로 실패시킨다. Glob/Grep으로 확인하는 데 몇 초면 된다. |
| "작업이 많으니 뒤쪽은 간단히 써도 되겠지" | 실행 에이전트는 앞뒤 작업을 구분하지 않는다. 마지막 작업도 첫 작업과 같은 상세도로 쓴다. |
| "verify는 실행할 때 알아서 정하면 된다" | verify 없는 작업은 실행자가 성공을 판단할 수 없어 재작업 루프를 만든다. 지금 정하라. |
| "추적성 매핑은 형식적이니 생략하자" | 매핑에서 빠진 SC 하나가 곧 스펙 위반 하나다. 5번 검증(spec-conformance-check)에서 터지는 것보다 지금 잡는 게 싸다. |
| "레이어별로 나누는 게 깔끔하다" | 수평 슬라이스는 마지막 통합까지 아무것도 검증 못 한다. 수직 슬라이스는 작업마다 동작을 전달한다. |
| "문서가 길어지니 판단 근거는 생략하자" | 판단 근거 없이는 사용자가 승인할 근거가 없고, 실행 중 수정 시 원래 의도를 잃는다. |

## 좋은 작업 지시 vs 나쁜 작업 지시

**나쁨**: "인증 로직을 개선한다."
**좋음**: "`src/auth/session.ts`의 `validateSession()`에 토큰 만료 검사를 추가한다. 만료 시 `TokenExpiredError`(이미 `src/errors.ts`에 정의됨)를 던진다. 기존 호출부 3곳(`api/middleware.ts:42`, ...)은 수정하지 않는다."

차이: 좋은 지시는 파일 경로, 사용할 기존 코드, 건드리지 말 범위를 모두 담아 실행자의 추측을 제거한다.

## 산출물 위치와 파일명

- 저장: `{프로젝트 루트}/docs/plan/YYYY-MM-DD-<계획-주제-kebab-case>.md`. 디렉터리가 없으면 생성한다.
- frontmatter의 `spec` 필드에 원본 스펙 문서 경로를 기록한다.
- 사용자가 다른 경로를 지정하면 그것을 따른다.
