# Plan Writer

고비용(고성능) 에이전트가 작업을 분석·설계하고, 저비용 에이전트가 그 계획대로 실행하는 워크플로우를 위한 스킬이다. 산출물은 단일 `PLAN.md` 파일이며, 사람과 에이전트가 모두 읽는다.

핵심 원칙: **계획을 읽는 실행자는 컨텍스트가 없고 추론 능력이 제한적이라고 가정하라.** "적절히 처리", "필요하면 리팩토링" 같은 판단을 요구하는 표현은 저비용 에이전트에게는 실패 지점이다. 판단은 계획 단계(지금)에서 끝내고, 실행 단계에는 명확한 지시만 남겨라.

## 작성 절차

1. **요구사항 인터뷰**: 전달받은 요구사항(기획서, 메시지, 구두 설명)을 그대로 받아 적지 마라. 사용자가 요청한 것과 실제로 원하는 것은 다를 수 있고, 요구사항 자체에 논리적 모순이 있을 수 있다. 인터뷰 방식:
   - 먼저 현재 이해를 한 문장 가설 + 확신도(%)로 제시한다. 확신도가 낮으면 무엇이 비어 있는지 한 줄로 덧붙인다.
   - 질문은 **한 번에 하나씩**, 각 질문에 나의 추측(GUESS)을 붙여서 한다. 사용자는 백지에서 답을 만들어내는 것보다 틀린 추측에 반응하는 게 빠르다.
   - 요구사항 간 모순(예: "기존 API 유지" + "응답 구조 변경"), 기존 코드·제약과의 충돌을 발견하면 즉시 지적하고 어느 쪽이 우선인지 확인한다. 모순을 안고 계획을 쓰면 실행 단계에서 반드시 터진다.
   - 요구사항을 검토하다 더 나은 접근이 보이면 근거와 함께 개선안을 제안하라. 단, 채택 여부는 사용자가 결정한다.
   - 종료 조건: 목표·성공 기준·제약·제외 범위를 사용자의 언어로 재진술했을 때 명시적 "예"를 받으면 끝. "알아서 해줘", "그렇게 하자" 같은 모호한 답은 확인이 아니다 — 구체적 선택지로 다시 물어라.
2. **컨텍스트 수집**: 대상 코드베이스를 직접 탐색하라(Glob/Grep/Read). 관련 파일의 실제 경로, 함수/클래스 이름, 기존 패턴·컨벤션을 확인한다. 추측으로 경로나 API를 쓰면 실행 에이전트가 존재하지 않는 파일을 찾다 실패한다. 코드를 확인하다 요구사항과 충돌하는 사실을 발견하면 1번으로 돌아가 사용자에게 확인한다.
3. **목표 정의**: 인터뷰에서 확인된 의도를 기준으로, 이 작업이 왜 필요한지·완료 시 무엇이 달라지는지 1~3문장으로 정리한다. 실행자가 모호한 상황에서 판단할 때 기준이 된다.
4. **작업 분해**: 독립적으로 검증 가능한 단위로 나눈다. 각 작업은 하나의 에이전트 세션에서 끝낼 수 있는 크기(대략 파일 1~5개 수정)로 한다. 작업 간 의존관계를 명시한다. 각 작업에 실행 등급(tier)을 지정한다. tier는 특정 모델명이 아니라 작업의 성격을 기술하며, 실제 모델 매핑은 실행 플랫폼(Claude, Codex, Antigravity 등)의 실행자가 결정한다:
   - `standard`(기본): 판단·추론이 필요한 작업. 여러 파일에 걸친 로직, 기존 패턴 추론, 디버깅 가능성이 있는 작업.
   - `light`: 명세가 완전한 기계적 작업에만 내린다. 정해진 파일의 정해진 변경, 보일러플레이트 생성, 단순 텍스트/설정 수정. 판단이 필요 없는 작업인지 자문하고, 확신이 없으면 standard로 둔다 — 저성능 모델의 실패·재시도 비용이 단가 차이를 잠식한다.
5. **PLAN.md 작성**: `references/plan-template.md`를 읽고 그 템플릿을 그대로 따라 작성한다.
6. **자체 검토**: 작성 후 실행 에이전트의 입장에서 다시 읽어라. "이 문서만 보고 코드베이스를 처음 보는 에이전트가 작업을 끝낼 수 있는가?"에 아니오가 나오는 부분을 보강한다. 특히 파일 경로가 실재하는지, 검증 명령이 실제로 실행 가능한지 확인한다.
7. **승인 요청**: 문서를 `status: draft`로 저장하고 사용자에게 제시한다. 판단 근거와 범위를 중심으로 검토를 요청하고, 실행(plan-executor)은 사용자가 승인한 뒤에만 진행됨을 안내한다. 계획을 작성한 세션이 곧바로 실행까지 이어가지 않는다 — 승인 게이트가 이 워크플로우의 통제 장치다.

## 타협 금지 (Anti-Rationalization)

계획 작성이 길어질수록 "이 정도면 되겠지"라는 타협이 생긴다. 아래 변명이 머릿속에 떠오르면 그것은 절차를 건너뛰라는 신호가 아니라 **건너뛰고 있다는 경고**다.

| 떠오르는 변명 | 실제 |
|---|---|
| "요구사항이 충분히 명확하다" | 목표·성공 기준·제약·제외 범위를 한 문장씩 쓸 수 없다면 명확하지 않은 것이다. 인터뷰를 하라. |
| "질문을 많이 하면 사용자 시간을 뺏는다" | 질문 몇 개의 비용은 작다. 잘못된 계획으로 저비용 에이전트 여러 개가 헛수고하는 비용이 훨씬 크다. |
| "경로/함수명은 대충 이럴 것이다" | 추측한 경로 하나가 실행 에이전트 하나를 통째로 실패시킨다. Glob/Grep으로 확인하는 데 몇 초면 된다. |
| "작업이 많으니 뒤쪽은 간단히 써도 되겠지" | 실행 에이전트는 앞쪽 작업과 뒤쪽 작업을 구분하지 않는다. 마지막 작업도 첫 작업과 같은 상세도로 쓴다. |
| "verify는 실행할 때 알아서 정하면 된다" | verify 없는 작업은 실행자가 성공 여부를 판단할 수 없어 재작업 루프를 만든다. 지금 정하라. |
| "문서가 길어지니 판단 근거는 생략하자" | 판단 근거가 없으면 사용자는 계획을 승인할 근거가 없고, 실행 중 수정 시 원래 의도를 잃는다. |

## 문서 포맷 규칙

- 포맷은 **Markdown 본문 + YAML frontmatter**. frontmatter는 오케스트레이터나 스크립트가 파싱하는 기계용 메타데이터, 본문은 사람·에이전트가 읽는 가이드다.
- frontmatter의 `tasks` 목록은 본문의 작업 섹션과 1:1로 대응해야 한다(`id` 기준). 어긋나면 자동화가 깨진다.
- 각 작업에는 반드시 **완료 기준(acceptance)과 검증 방법(verify)** 을 포함하라. 검증 방법은 가능한 한 실행 가능한 명령(테스트, 빌드, curl 등)으로 쓴다. 실행자가 스스로 성공 여부를 판단할 수 있어야 재작업 루프가 줄어든다.
- 하지 말아야 할 것(out of scope)을 명시하라. 저비용 에이전트는 시키지 않은 "개선"을 하는 경향이 있다.
- **판단 근거(Rationale)** 섹션을 반드시 포함하라. 왜 이 접근을 택했는지, 검토했다가 버린 대안과 그 이유, 트레이드오프를 기록한다. 사용자가 계획을 승인하기 전에 계획자의 판단이 타당한지 검토하는 근거가 되고, 실행 중 계획을 수정해야 할 때 원래 의도를 지키는 기준이 된다.

## 좋은 작업 지시 vs 나쁜 작업 지시

**나쁨**: "인증 로직을 개선한다."
**좋음**: "`src/auth/session.ts`의 `validateSession()`에 토큰 만료 검사를 추가한다. 만료 시 `TokenExpiredError`(이미 `src/errors.ts`에 정의됨)를 던진다. 기존 호출부 3곳(`api/middleware.ts:42`, ...)은 수정하지 않는다."

차이: 좋은 지시는 파일 경로, 사용할 기존 코드, 건드리지 말 범위를 모두 담아 실행자의 추측을 제거한다.

## 산출물 위치와 파일명

서비스 코드에 영향을 주지 않도록 계획 문서는 프로젝트 루트가 아닌 별도 문서 경로에 저장한다.

- 기본 경로: `{프로젝트 루트}/docs/` 아래에 문서 성격별 하위 디렉터리를 만든다. 예: `docs/plan/`(작업 계획), `docs/spec/`(요구사항·설계 명세). 디렉터리가 없으면 생성한다.
- 파일명은 생성 시점과 계획 내용을 담아 `YYYY-MM-DD-<계획-주제-kebab-case>.md` 형식으로 한다. 예: `docs/plan/2026-07-06-session-token-refresh.md`. 목록만 봐도 언제 무슨 계획인지 알 수 있어야 한다.
- 사용자가 다른 경로를 지정하면 그것을 따른다.
