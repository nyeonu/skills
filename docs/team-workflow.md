# 팀 협업 운영 규칙 — 스펙·티켓·브랜치

이 문서는 **사람**을 위한 것이다. 이 워크플로우를 처음 접한 팀원이 "스펙은 어디에 쓰고, 티켓은 어떻게 만들고, 작업 중에 스펙이 바뀌면 어떻게 하나"를 한 번에 파악하도록 쓴다. 에이전트가 따르는 규칙은 각 스킬의 SKILL.md와 템플릿에 있고, 이 문서는 그 규칙의 **모양과 이유**를 설명한다. 둘이 다르면 스킬 파일이 우선이고 이 문서를 고친다.

## 1. 용어

- **애플리케이션**: 따로 배포되고 따로 담당자가 있는 단위. 예: fanclub-auth, fanclub-service-api. 계약, 담당, 배포 순서는 전부 이 경계 기준이다.
- **저장소**: git 저장소. 문서가 놓이는 위치와 브랜치를 말할 때만 쓴다. fanclub처럼 저장소 하나가 애플리케이션 하나면 둘이 겹치고, 모노레포면 갈라진다.
- **통합 브랜치**: 한 변경의 코드와 문서가 모이는 브랜치. 에픽 티켓 번호로 브랜치를 따고 그 밑에 작업 브랜치를 두는 팀이면 에픽 브랜치(예: `feature/ASD-2141`)이고, 그런 층이 없으면 main이다.
- **계약(contract)**: 애플리케이션 사이의 약속. API 요청·응답 형식, DB 스키마, 이벤트 스키마, 캐시 키처럼 "내 코드와 네 코드가 만나는 지점"의 정의.
- **additive 변경**: 기존 소비자를 깨지 않고 더하기만 하는 변경. 예: 응답에 선택 필드 추가.

## 2. 문서 세 가지의 역할

| 문서 | 답하는 질문 | 읽는 사람 | 다루는 단위 | 언제 바뀌나 |
|---|---|---|---|---|
| 스펙 (docs/spec/) | 왜 하는가, 무엇이 달라지는가, 무엇이 되면 끝인가(SC), 밖에서 보이는 약속(계약) | 사람 전원 + 에이전트 | 기능, 애플리케이션, API 엔드포인트 | 요구사항이나 계약이 바뀔 때 |
| ADR (docs/decisions/) | 왜 이 방법을 골랐고 무엇을 포기했나 | 나중에 "왜 이렇게 했지" 묻는 사람 | 되돌리기 비싼 결정 하나 | 결정이 뒤집힐 때 |
| 계획 (docs/plan/) | 어느 파일을 어떤 순서로 어떤 테스트로 바꾸는가 | 에이전트. 사람은 승인용 앞부분만 | 파일, 함수, 테스트 케이스 | 구현 방법이 바뀔 때 |

판별법: **구현 방법을 바꿔도 그 문장이 그대로 유효하면 스펙, 구현을 바꾸면 문장이 바뀌면 계획.** API의 요청·응답 형식은 언뜻 "어떻게"처럼 보이지만 저장소 밖에서 관찰되는 약속이라 스펙이다.

예:
- 스펙: "fanclub-service-api가 부가정보를 새 API `GET /v2/membership/extra`로 조회하고 기존과 동일한 결과를 낸다."
- 계획: "`MembershipClient.getExtra()`의 URL을 v2로 바꾸고 `memberId` 파라미터 매핑을 추가한다."
- ADR: "기존 v1을 즉시 삭제하지 않고 전환 완료까지 유지한다. 동시 배포 조율 비용보다 한 스프린트 중복 운영이 싸다."

## 3. 스펙의 범위: 공통 스펙과 애플리케이션 스펙

스펙 frontmatter의 `scope`는 두 값이다.

| scope | 뜻 | 쓰는 사람 | 위치 |
|---|---|---|---|
| `app` | **애플리케이션 스펙.** 애플리케이션 하나가 자기 안에서 할 일. 단독 변경이면 이것 하나로 끝. 공통 스펙의 일부면 `parent`로 공통 스펙을 가리킨다 | 그 애플리케이션 담당자 | 그 애플리케이션 저장소의 `docs/spec/` |
| `shared-app` | **공통 스펙.** 여러 애플리케이션이 함께 바뀌는 변경에서 **함께 알아야 하는 것**만: 왜 하는가, 계약, 배포 순서, 통합 성공 기준, 참여자(`participants`) | 관련 담당자 전원이 논의 자리에서 함께 | 계약을 제공하는 쪽 저장소의 `docs/spec/`, 통합 브랜치 |

나누는 기준은 애플리케이션 경계가 아니라 **"양쪽이 같이 알아야 하는 것"과 "한쪽만 알면 되는 것"의 경계**다. 계약을 두 곳에 적으면 반드시 어긋난다. 그래서 계약은 공통 스펙 한 곳에만 쓰고, 애플리케이션 스펙은 참조만 한다. 반대로 fanclub-auth가 기존 API를 어떻게 정리하는지, fanclub-service-api가 캐시를 어떻게 갱신하는지는 상대에게 소음이라 각자의 스펙에만 둔다.

**예시 — 인증 서버의 API 두 개를 교체하고 서비스 API가 새 API를 쓰도록 바꾸는 작업:**

| | 변경 전 (애플리케이션별로 독립 작성) | 변경 후 (공통 스펙 하나 + 애플리케이션 스펙 둘) |
|---|---|---|
| fanclub-auth | `docs/spec/api-replace.md`<br>· 새 API 경로·파라미터·응답 **(중복)**<br>· 기존 API 정리 | `docs/spec/…-ASD-2141-membership-api.md` — `scope: shared-app`<br>· 새 API 경로·파라미터·응답 **(유일한 원본)**<br>· 배포 순서, 통합 SC<br><br>`docs/spec/…-membership-api-provider.md` — `scope: app`, `parent` → 위 공통 스펙<br>· 새 API 구현, 기존 API 정리 |
| fanclub-service-api | `docs/spec/api-replace.md`<br>· 새 API 경로·파라미터·응답 **(중복)**<br>· 호출부 변경, 캐시 | `docs/spec/…-membership-api-consumer.md` — `scope: app`, `parent` → fanclub-auth 저장소의 공통 스펙<br>· 호출부 변경, 캐시 |

**링크는 자식 → 부모 한 방향이다.** 애플리케이션 스펙의 `parent`가 공통 스펙을 가리키고, 공통 스펙은 자식 목록을 갖지 않는다. 부모에 자식 목록을 두면 자식을 쓸 때마다 부모를 고치는 되돌이 커밋이 생기고, 자식이 다른 저장소에 있어 그 커밋은 항상 따로 간다. 대신 공통 스펙은 `participants`(참여 애플리케이션과 담당자)를 갖는다. 이 값은 논의 자리에서 이미 정해지므로 작성 시점에 확정되고 이후 바뀌지 않는다. 자식을 찾아야 하면 각 참여 저장소의 `docs/spec/`에서 `parent:` 값을 검색하고, 사람이 보는 실시간 목록은 Jira 에픽의 하위 티켓이 맡는다.

## 4. 사람이 기억할 네 단계

| 단계 | 누가 | 하는 일 | 끝의 표시 |
|---|---|---|---|
| 1 | 스펙 담당자 | 통합 브랜치를 따고 AI(spec-writer)와 스펙 작성. 관련자와 검토 | 스펙 티켓 완료 = 승인. frontmatter `approved` |
| 2 | 각 개발 담당자 | 통합 브랜치에서 작업 브랜치를 따고, AI와 애플리케이션 스펙·계획 작성 후 구현 | 스토리 PR이 통합 브랜치에 머지 |
| 3 | 검증 담당자 | 통합 SC 확인 | 통합 검증 티켓 완료 |
| 4 | 에픽 담당자 | 통합 브랜치를 main에 머지 | 에픽 완료 |

이게 전부여야 한다. scope, parent, 변경 등급, 계약 방식 같은 것은 템플릿과 스킬 안의 규칙이고, 사람은 "스펙 담당자가 AI로 스펙을 쓴다"까지만 알면 된다. 스킬이 나머지를 강제한다.

작업 중 장애 대응으로 빠졌다가 돌아와도, 다른 사람이 이어받아도 상태를 잃지 않는 이유는 상태가 사람 머리가 아니라 세 곳에 있기 때문이다. 티켓 상태(누가 어디까지), 문서 frontmatter(승인됐나, 끝났나), 브랜치(코드가 어디에). 이 셋을 읽으면 중단 지점이 나온다.

## 5. 티켓 모양

티켓은 "누가 무슨 일을 하고 있고 끝났나"를 담는다. 문서를 티켓으로 미러링하지 않고, **에픽마다 항상 같은 모양**을 만든다. 조건에 따라 티켓이 있고 없고를 외우게 하지 않는다. 애플리케이션 하나짜리 작업이어도, 스펙 작성자와 개발 담당자가 같은 사람이어도 모양은 같다.

```
에픽
├─ 스펙                 ← 스펙 담당자. 완료 = 승인. 공통 스펙(애플리케이션 하나면 그 애플리케이션 스펙)을 링크
├─ <애플리케이션 A>     ← 개발 담당자. 애플리케이션 스펙·계획·구현·PR이 전부 이 안에서 진행된다
├─ <애플리케이션 B>     ← 같음. participants 항목마다 하나
└─ 통합 검증            ← participants가 둘 이상일 때만. 공통 스펙의 통합 SC 검증 담당자
```

- 에픽과 스펙 티켓은 요구사항 접수 시 사람이 만든다. 아직 스펙이 없으므로 여기까지는 손이다.
- 애플리케이션별 스토리와 통합 검증 티켓은 **승인된 스펙의 `participants`에서 파생**한다. 만드는 쪽(사람 또는 앞으로 만들 ticket-writer)은 애플리케이션 이름을 미리 알 필요가 없다.
- `parent`가 있는 애플리케이션 스펙은 티켓을 만들지 않는다. 그 담당자만 읽는 문서라 추적할 것이 없고, 스토리의 첫 단계일 뿐이다.
- 스펙 승인이 티켓 상태(사람용)와 frontmatter(에이전트용) 두 곳에 남는데, 행위는 하나다. 스펙 담당자가 티켓을 완료로 옮기는 순간 frontmatter도 바꿔 push한다.

## 6. 브랜치 모양

- **공통 스펙은 통합 브랜치에서 관리한다.** 요구사항 접수 시 통합 브랜치를 따면 스펙 커밋이 첫 커밋이 된다. 통합 브랜치가 main에 머지될 때 문서도 함께 들어가므로 별도 절차는 없다.
- **상대 애플리케이션 담당자는 상대 저장소의 같은 이름 통합 브랜치를 읽는다.** 브랜치명이 티켓 번호로 정해지므로 찾을 수 있다. 작업 브랜치 안의 미머지 스펙을 상대가 읽게 하지 않는다.
- **작업 브랜치는 통합 브랜치에서 따고, 통합 브랜치를 당겨 받는다.** 코드에 대해 이미 하는 일이라 새 습관이 아니다.
- **스펙 변경 때문에 브랜치를 오가지 않는다.** 자기 애플리케이션 스펙 내부 수정은 작업 브랜치에서 그냥 커밋한다. 계약 변경(아래 L1·L2)만 통합 브랜치에 직접 커밋한다. 빈도가 낮고, `git worktree`로 통합 브랜치를 옆 디렉터리에 열어두면 전환 없이 파일 하나 고쳐 push하면 끝이다. 작업 브랜치에 넣고 PR 머지를 기다리면 그동안 상대가 낡은 계약을 보게 되므로 피한다.
- **스펙 변경 커밋은 코드 커밋과 섞지 않는다.** 메시지 접두어를 `spec:`으로 통일하면 이력에서 계약이 언제 움직였는지 보인다.

## 7. 승인된 스펙이 바뀔 때

목표는 승인을 받는 것이 아니라 **말로 합의한 결과가 30초 안에 문서에 반영되는 것**이다. 구두는 합의 수단이고 문서는 기록 수단이다. 기록은 그 자리에 없던 사람과 AI 에이전트를 위한 것이다. 에이전트는 대화에 없었으므로, 갱신되지 않은 스펙을 진실로 믿고 작업한다. 절차가 무거우면 사람은 우회하고, 우회된 스펙은 에이전트가 믿는다. 그래서 절차는 가볍게, 반영은 즉시다.

| 등급 | 어떤 변경 | 절차 |
|---|---|---|
| L0 | 자기 스펙 내부. 문구, 확인값 갱신, 미해결 사항 해소, 애플리케이션 스펙의 내부 내용 | 그냥 커밋. 알림 없음 |
| L1 | 계약 변경이지만 additive한 것 (예: 응답에 선택 필드 추가) | 커밋 + 알림(Slack 또는 Jira 댓글). 이의 없으면 확정 |
| L2 | 깨지는 계약 변경. 필드 삭제·의미 변경, 필수 파라미터 추가, 배포 순서 변경 | `participants` 담당자 확인 필수. 확인 방법은 구두 합의 후 커밋 메시지에 기록, 또는 PR 중 팀이 고른다 |

- PR은 게이트가 아니라 **상대가 부재일 때 확인을 비동기로 받는 도구**다. 옆에 있으면 말로 합의하고 커밋 메시지에 `OOO와 구두 합의`라고 남기면 같은 효력이다.
- 워크플로우의 승인 게이트(스펙 승인, 계획 승인)는 문서 최초 승인에만 걸린다. 이후 변경은 그 게이트를 다시 타지 않고, **스펙 티켓도 다시 열지 않는다.**
- 요구사항 자체가 바뀌어 스펙을 사실상 다시 써야 하면 수정이 아니라 새 변경이다. 새 에픽 또는 새 스펙 티켓이고, 옛 스펙은 `superseded`가 된다.

| | 문서로 기록 | 구두로만 |
|---|---|---|
| 부재·휴가·인수인계 | 이력이 남아 이어받을 수 있음 | 사라짐 |
| AI 에이전트 | 최신 계약을 읽고 작업 | 대화에 없었으니 낡은 스펙을 믿고 작업 |
| 어긋남 발견 시점 | 커밋 시점 | PR 또는 배포 시점 |
| 소통 비용 | 커밋 1회, L1 이상은 알림 1회 | 말 한마디 |
| 실패 양상 | 절차가 무거우면 우회되고, 우회된 스펙은 AI가 믿음 | 사람 수가 늘거나 시간이 지나면 기억이 갈라짐 |

## 8. 스펙의 수명과 계약 파일

스펙은 시스템의 현재 상태를 설명하는 문서가 아니라 **변경 하나에 대한 기록**이다. 구현이 끝난 뒤 코드가 어떻게 바뀌어도 "그때 왜 이걸 했고 무엇이 되면 끝이었나"는 변하지 않으므로, **완료 후 코드에 맞춰 스펙을 고치지 않는다.** 대신 진행 중에 SC나 범위가 바뀌면 그 순간 스펙을 고친다(7절). 완료 시점에 스펙과 결과물의 차이는 0이어야 하고, 그 확인이 spec-conformance-check의 일이다.

| status | 뜻 | 누가 바꾸나 |
|---|---|---|
| `draft` | 작성 중 | spec-writer |
| `approved` | 승인됨. 계획 분해(task-breakdown)의 입력이 되는 유일한 상태 | 사용자 승인 시 spec-writer |
| `implemented` | 구현 완료. 기록으로만 남는다 | spec-conformance-check가 전체 PASS를 낸 뒤 |
| `superseded` | 나중 스펙이 이 스펙의 계약이나 결정을 대체함 | 대체하는 스펙을 쓰는 spec-writer |

완료 후 문서 정리는 이렇게 된다.

| 문서 | 완료 후 | 이유 |
|---|---|---|
| 계획 (PLAN.md) | 삭제해도 됨 | 순수한 "어떻게"라 끝나면 가치가 없고 git 이력에 남음 |
| 스펙 | 손대지 않음. 상태만 `implemented` | 변경 기록. 코드에 맞춰 고치면 "그때 무엇을 약속했나"가 사라짐 |
| ADR | Accepted로 확정. 이후 손대지 않음 | 결정 기록. 뒤집히면 새 ADR |
| 계약 파일 | 코드와 함께 살아 있음 | 아래 참고 |

**"지금 유효한 계약이 뭐지"의 답은 스펙이 아니라 계약 파일이다.** 스펙은 요구사항 접수 직후에 쓰므로 그 시점에 새 API는 코드에 없고, springdoc 같은 생성 문서는 있는 코드만 그려낸다. 그래서 팀 방식에 따라 갈린다.

| | 계약 우선 (contract-first) | 코드 우선 (code-first, springdoc) |
|---|---|---|
| 개발 전 계약의 원본 | 손으로 쓴 openapi.yaml. 스펙과 함께 커밋 | **스펙 4절의 계약 표** |
| 개발 후 계약의 원본 | 같은 파일. 코드가 이 파일에 맞는지 테스트 | springdoc 출력. 구현 PR에서 생성 문서를 파일로 스냅샷 커밋하고 "생성 결과 == 파일" 테스트 |
| 소비자가 병렬로 시작할 수 있나 | 있음. 파일에서 클라이언트 생성 | 표를 보고 시작. 제공자 구현 후 스냅샷으로 검증 |

생성 문서는 코드와 어긋나지 않지만 그것은 "현황"이지 "약속"이 아니다. 개발자가 필드명을 바꾸면 생성 문서도 조용히 바뀌고 소비자는 깨진 뒤에야 안다. 스냅샷 파일과 비교 테스트가 있어야 계약 변경이 diff로 드러나고, L1(더하기)과 L2(깨짐)를 기억이 아니라 diff로 판별할 수 있다. Jira나 다른 문서에 계약을 다시 적지 않는다. 정보는 한 방향으로만 흐른다. 코드 → 계약 파일(테스트로 강제) ← 스펙이 버전을 가리킴 ← Jira가 스펙을 링크.

## 9. 흐름도는 어디에, 얼마나

원칙은 **문장과 표로 안 보이는 것만 그린다.** 여러 애플리케이션을 거치는 호출 순서, 상태 전이, 저장소(캐시·DB·큐) 사이의 데이터 이동이 그것이다.

| 문서 | 그림 | 수준 |
|---|---|---|
| 공통 스펙 4절 | 애플리케이션 간 호출 순서를 **변경 전/후** 시퀀스 다이어그램으로. 배포 순서와 함께 계약의 일부 | 노드는 애플리케이션과 API 엔드포인트까지 |
| 애플리케이션 스펙 | 원칙적으로 없음. 상태 전이, 비동기·이벤트, 캐시 갱신 순서, 여러 메소드에 걸친 트랜잭션 중 하나에 걸릴 때만 | 컴포넌트까지 |
| 계획 | 없음. 에이전트에게는 파일 경로와 함수명이 그림보다 정확하다 | |
| PR | 스펙의 그림을 가져다 쓴다. 새로 그리지 않는다 | |

바뀌는 경로만 그린다. 로그인이 안 바뀌면 "로그인 완료" 노드 하나로 접는다. 판별법으로, 기능을 말로 설명할 때 "그다음에", "만약 ~상태면"이 세 번 이상 나오면 그린다. 형식은 Mermaid 텍스트다. 이미지와 달리 에이전트가 읽을 수 있고 diff가 남는다.

## 10. ADR의 위치

ADR은 결정 하나의 기록이라 문서 계층이 아니라 **결정의 소유자**를 따라간다.

| 결정의 성격 | ADR 위치 | Jira에서 링크하는 곳 |
|---|---|---|
| 계약 수준. 예: 기존 API를 버전 올려 유지할지 교체할지, 배포 순서 | 공통 스펙과 같은 저장소의 docs/decisions/ | 에픽 |
| 애플리케이션 수준. 예: 부가정보를 캐시할지 매 요청 조회할지 | 그 저장소의 docs/decisions/ | 해당 스토리 |

## 11. 낡은 계획을 기계로 잡는 장치

계획(PLAN.md)의 frontmatter에는 참조한 스펙의 커밋 해시(`spec_rev`, parent가 있으면 `parent_spec_rev`)가 들어간다. plan-executor는 실행 전에 이 값과 현재 스펙의 커밋을 비교해서, 계획을 세운 뒤 스펙이 바뀌었으면 멈추고 무엇이 바뀌었는지 보여준다. 7절의 "30초 안에 반영"이 지켜지는 한, 스펙 변경이 낡은 계획으로 코드가 되는 일은 사람의 기억이 아니라 이 비교가 막는다.

## 12. 아직 정하지 않은 것

- **ticket-writer**: 승인된 스펙의 `participants`를 읽어 5절의 티켓 모양을 에픽 아래 생성하는 스킬. 티켓 생성만 하고 상태 동기화는 하지 않는다.
- **pr-writer**: 티켓(왜), 계획의 선택 이유, diff, conformance 결과를 읽어 PR 본문 템플릿을 채우는 스킬.
- 코드 우선 팀을 위한 계약 스냅샷 테스트 패턴(생성 문서 == 커밋된 파일)을 참고자료로 정리하는 것.
